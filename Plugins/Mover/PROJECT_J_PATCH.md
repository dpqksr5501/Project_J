# Project J Mover lifecycle patch

The project plugin overrides Epic's Mover because it consumes the project NetworkPrediction override. The lifecycle patch below is based on the installed UE 5.8.4 / 58902052 sources. Other Mover behavior and Epic copyright headers are preserved.

`UKinematicActorSimulation::BeginDestroy` releases its UObject references without invoking runtime `Uninit`. Both liaison implementations already call `Uninit` from EndPlay/UninitializeComponent (and simulation replacement). Garbage collection has no ordering guarantee between the simulation and its FSM: the FSM can have cleared its queued transition before the simulation starts destruction. Runtime clear also constructs replacement default modes, which must not run while collecting the object graph.

An explicit `Uninit` ignores an FSM whose destruction has already begun. Normal runtime mode deactivation/unregistration remains in `Uninit`; movement reset APIs retain their behavior. No installed engine files are modified.

Regression: `ProjectJ.Foundation.Mover.DestructionOrder`, original `ProjectJ.Continuation.NPCRegistrationCallbackGC` / `NPCResultBroadcastGC`, and their original mixed audit roster. A focused test explicitly exercises both destruction orders and checks that teardown does not create replacement modes.

The protected `RegisterDefaultSharedSettings` hook lets the project component constructor register an owned native default subobject with the existing settings collection. It requires the default-subobject flag and movement-settings interface. `RefreshSharedSettings` keeps its runtime ownership and matching/removal behavior; no parallel settings collection is added. The project registers `CommonLegacyMovementSettings_0`, preserving the native template identity already referenced by serialized Blueprint/level settings. The former project `PostInitProperties` dynamic creation is removed. A fresh packaged UI run found that dynamic object absent from native script imports even though Editor tests and Cook succeeded. Native identity/per-instance tests and another fresh Cook/package validate this boundary; no installed engine files are modified.

`USmoothWalkingMode` uses `MinimalAPI` so the project Core module can derive a native walking implementation. This exports the generated constructor/destructor/vtable helpers; existing virtual solver methods already carry the Mover API. No movement settings, state layout, spring implementation or simulation code changes. `UProject_JGroundWalkingMode` calls the existing project ground solver directly. The generated `GenerateWalkMove` event still respects Blueprint overrides; only an explicitly migrated thin adapter can inherit the native branch. Blueprint settings/graph preservation and runtime performance require separate validation before adoption.

Exact native Flying prediction may opt in to query-local parameter preparation with `mover.Prediction.ReuseFlyingParams` (default0). The original GenerateMove and prediction share one private native builder using the existing cached settings. Only synchronous GT queries with default state/time, no optional inputs, unbased input/sync and explicit nonzero facing reuse its value result. Prior velocity/orientation/time and the original free-move solver run for every unchanged sample. Other queries retain ordinary dispatch. No reflected layout, retained cache, worker UObject access or simulation-quality change is introduced. Numerical and same-binary workload validation are required before project enablement.

The project enables this guarded path in DefaultEngine.ini after 92-sample value/fallback tests and one same-binary rendered200 OFF/ON pair: attack scope interval median9.6011->6.6162ms, equal6600 calls per measured attack group. This is a local workload result with full-quality local/avatar, weapon and cloth checks; no general FPS/capacity guarantee. Shared deployment validation is tracked with the next gameplay checkpoint.
