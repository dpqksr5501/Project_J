# Project_J — 8×8km MMORPG 시작 권역 전체 제작 및 차기 권역 확장 아키텍처 (Codex 실행 지시서 v4)

> **현재 목표:** 이미 구현된 Project_J의 8×8km 규모 Lv.1~30 시작 권역을 **실제 플레이 가능한 고품질 중세 판타지 오픈월드**로 단계적으로 완성한다. 지도에서 후보로 보이는 장소가 아니라, 도시·마을·사냥터·필드 보스·바이옴·동선이 실제 에디터와 플레이 환경에 구현되어야 한다.
>
> **장기 목표:** 이번 권역의 지형·도로·바이옴·정착지·사냥터·보스 데이터/생성 시스템을 재사용하여 향후 Lv.31~100 신규 지역을 추가할 수 있도록 한다. 이번 작업에서 Lv.31+ 지역 콘텐츠 전체를 미리 제작할 필요는 없다.
>
> **프로젝트:** `Project_J` (기존 프로젝트/현행 작업 브랜치 기준). 언리얼 엔진은 사용자가 앞서 지정한 **UE 5.8 기준**으로 검토하되, 실제 설치된 빌드와 플러그인 버전을 먼저 조사한다.
>
> **참고 자료:** 이전 `WorldGen_Prompt_v3.md`, `ZONE_LAYOUT_LV1_30.json`, 게임 스크린샷 레퍼런스, 8×8km 탑뷰 목표 이미지 및 사용자가 현재 공유한 Unreal Editor 스크린샷. **이 문서가 '실행 및 최종 산출물/확장성'의 최신 기준**이다. 원본 자료 사이에 충돌이 있으면 사용자 지시 → 이 문서 → 기존 프로젝트의 사실/게임플레이 호환 → v3 부록/JSON의 기획 좌표 → 이미지 순으로 검토하되, 기존 코드·높이 데이터의 무단 파괴는 금지한다.

## 0. 이 요청에 대한 작업 원칙 — 계획에서 멈추지 말 것

1. **실제로 구현하는 작업이다.** 현재 구현을 짧게 조사하고 체크리스트와 마이그레이션 대응표를 작성한 다음, 안전한 범위에서는 곧바로 Phase 1부터 구현한다. 모든 Phase를 설명만 하고 종료하지 않는다.
2. 한 번의 세션에 8×8km 전역의 AAA급 완성도가 실현된다고 주장하지 않는다. **실행 가능한 분량을 실제로 구현 → 에디터 검증 → 결과 기록 → 다음 Phase로 계속 진행**한다. 세션/컨텍스트/시간이 끊기면 인수인계 파일을 남긴다. 장기 작업의 최종 목표를 임의 축소하지 않는다.
3. **기존 Project_J의 산체·고도 원본, 레벨, 기존 C++/Blueprint, 캐릭터·전투·이동 시스템, 기존 임포트 에셋 및 공급자 원본을 보존한다.** 지형 보정은 원본을 변형하지 않는 Edit Layer/파생 데이터 등으로 수행한다. 반드시 원본 자체를 수정해야 할 경우 구체적 이유·영향 범위·복원 방법을 먼저 설명하고 승인받는다.
4. **기존 월드의 생성 결과를 읽고 이어서 작업한다.** 이전에 생성된 도로·교량·성문·시작 마을과 18개 위치 후보를 처음부터 중복 생성하지 않는다. 현존 장소와 아래 필수 ID를 매핑하여 유지/개선/미구현을 구분한다.
5. 새 시스템 개발보다 **검증된 기존 시스템의 재사용을 우선한다.** 이미 구현된 `C++/PCG/Material/AI/Spawn` 기능은 이름·입력·출력·의존성·성능을 파악하고 재사용 또는 확장한다. 기존 사용자 경험을 깨는 구조 변경은 승인받는다.
6. UE MCP는 실제 이용 가능한 Toolset과 권한을 확인한다. PCG/Material/Landscape 기능이 MCP에 없으면 검증된 Editor Utility, Editor Python, C++ Editor Module, Commandlet 등으로 보완한다. **실행하지 않은 도구나 검증하지 않은 결과를 완료했다고 말하지 않는다.**
7. 고밀도 자연환경은 **고품질을 목표로 하되 성능 예산 안에서 구성**한다. 정적 월드 콘텐츠는 에디터에서 생성·저장하는 방식을 우선 검토하며, 클라이언트 렌더링과 서버 게임플레이를 혼동하지 않는다.
8. 날씨 시스템은 **명시적으로 보류**한다. 날씨보다 월드의 지형, 공간, 수계, 바이옴, 거주지, 이동/게임플레이, 최적화에 집중한다.
9. **각 Phase별 완료 판정은 실제 아티팩트와 검증 근거**로 수행한다. '코드 작성', '배치 후보 생성', '빌드 성공'만으로 레벨 디자인 완료라고 표시하지 않는다.
10. 기존 사용자 요구인 **검은사막형 현실적 규모감과 자연환경**을 지향하되, 검은사막의 고유 지형·도시·메시·IP를 복제하지 말고 Project_J만의 독창적인 환경을 구성한다.

## 1. 무엇을 최종적으로 만들어야 하는가: 20개 핵심 장소 + 연결 월드

### 1.1 필수 정착지 9곳 (S01~S09)

기존 맵의 실제 자산과 공간 규모에 따라 배치 좌표 및 명칭은 수정 가능하지만, **역할과 서로 구분되는 디자인 구조는 유지**한다. 기존 시작 마을은 적절한 S ID로 매핑해 재사용한다. 중복 지명을 피하고 기존 게임플레이 참조를 보존한다.

| ID | 규모/역할 | 필수 시각·공간 구성 | 최소 검증 |
|---|---|---|---|
| **S01 중앙 성곽 수도** | 대형 / 핵심 허브 | 다중 성문, 성곽, 성채 또는 중심 랜드마크, 중앙 광장, 시장, 상업·주거·공방 구역, 불규칙 골목, 외곽 농지, 2개 이상의 도시 접근축 | 플레이어가 주요 도로에서 들어가 광장과 기능 구역까지 이동. 건물 위치·높이·구역 밀도 차별화 |
| **S02 농업 마을** | 중형 / 초기 생활·성장 | 밭·과수·풍차 또는 방앗간·헛간·우물·농로·울타리·곡물 저장 시설 | 주거지와 경작지가 연결, 농촌 특유의 뚜렷한 윤곽 |

**수량 정책:** 수도 1 + 중형 마을 5 + 소규모 취락·거점 3 = 9곳. v3의 `정착지 7개` 또는 기존 `18개 후보 장소`와 정확히 매핑하고, 기존 완성 장소가 있으면 새로 만들지 말고 해당 ID에 편입한다. 향후 게임 디자인상 더 필요한 정착지는 추가하되 필수 9개 구현을 가리지 않는다. 임시 건물 수를 억지로 늘려 목표 수를 채우지 않는다.

**S01 수도의 필수 내부 구조:** 
- 도시 실루엣(중심 랜드마크·성벽·건물 높이 계층)을 멀리서 알아볼 수 있을 것.
- 최소 4종의 가로 성격(대로/시장거리/주거 골목/서비스·뒷골목). 격자 복제 금지.
- 도로 위계→필지→건물 배치→마당·생활 소품→수동 아트 디렉션 순서.
- 필요한 경우 Level Instance/Packed Level Actor로 반복 가능한 작은 건축 군집을 모듈화하되, 전체 도시가 똑같은 군집의 반복이 되지 않도록 변형/수동 제어.
- 도시 전체와 외곽/시작 마을, 강·교량, 주변 농지 연결. 정문 앞만 꾸미고 도시 내부를 비워 놓지 말 것.

### 1.3 필드 보스 2곳 (B01~B02)

- **B01 암릉의 수호자**: 북서 암반 고지. 넓은 전투 지형, 여러 접근로, 안전 집결지, 낙하 및 고도 차 관리, 근접/원거리 공격 공간. Lv.25~30의 선택형 보스로 기획.
- **B02 고목의 파수자**: 동부 깊은 숲의 고대 유적. 수목 사이 전투 공간, 뿌리·지형 엄폐, 전투 리셋 범위와 우회 통로. Lv.28~30 선택형 보스로 기획.

두 보스 모두 `Location + Arena + Approach + Safe Staging + Encounter Data`를 실제 월드에 구현한다. **완성 단계는 별도 표기:** 위치 후보 ≠ 아레나 블록아웃 ≠ 환경 아트 ≠ AI/스킬 구현 ≠ 멀티플레이 검증. 전투 시스템은 `Project_J` 기존 클래스·GAS/AI 구조를 확인한 뒤 통합할 것. AI·Spawn·보상/룻을 새로 복제하지 않는다. 중요 퀘스트/차기 권역 연결로를 보스가 차단하지 않게 한다.

### 1.4 주요 기반 시설 및 자연 랜드마크

- 대도로와 지역 간 연결 도로, 농로/숲길/산길·샛길의 **계층형 네트워크**와 필수 정착지·사냥터 접근 경로.
- 최소 3종의 **교량/도하 구조**(석조 대교·목교·산악형 협곡 다리 등)를 지형에 맞게 배치. 수량은 수계 적합성에 따라 검증하고 조정.
- 산악 등반 경로와 전망 포인트 3곳 이상, 자연스러운 협곡·암벽·넓은 구릉, 선택적으로 동굴/터널(기술·에셋 확인 후).
- 연속된 **산지 수원 → 지류 → 본류 → 호수/평야 → 하구/해안**. 지형에 반하는 역류/갑작스러운 물길 종료 금지.
- 지역별 시각적 실루엣이 달라야 함: 농경지, 울창한 대삼림, 큰 호수, 절벽, 항구, 고원/설산(필요한 경우), 강변 습지.
- 경계 확장 방향마다 기존 도로/수계/바이옴의 연장 가능 지점을 문서와 데이터로 지정.

## 2. 작업 시작 직후: 기존 18개 후보 및 콘텐츠 보존·대응표

## 3. 재사용 가능한 시스템 아키텍처 — 후속 Lv.31~100 권역을 위한 핵심

### 3.1 분리 원칙: 공통 엔진 ↔ 권역 설정 ↔ 실제 배치

**절대로 이번 8×8km의 지형 좌표·바이옴·건물 배치 로직을 C++ 클래스에 하드코딩해서 다음 권역에서 그대로 복제해야 하는 상태를 만들지 말 것.** 권장 논리 구조:

```text
Project_J (기존 게임플레이 계약 유지)
 ├─ Shared World Runtime             : Region/POI 조회, 동적 스폰 연동, 안전지대/레벨 권장 정보
 ├─ Shared World Editor Tools        : 지형 분석·수계/도로/정착지 계획·검증·리빌드
 ├─ Shared Content Generation        : PCG 서브그래프, 바이옴, 식생, 필지, 소품 배치
 ├─ Shared Environment Assets        : 마스터 머티리얼, 머티리얼 인스턴스, Foliage Types, 키트
 ├─ World / StarterRegion (Lv1~30)   : 현재 8×8km 데이터, 위치/높이 원본, 월드 상태, 배치 결과
 └─ World / FutureRegions (Lv31+)    : 향후 동일 계약을 따르는 별도 RegionProfile·에셋 구성
```

위 구조는 **논리적 책임 구분 예시**이며 프로젝트 폴더/모듈을 무조건 이 이름으로 재조직하라는 뜻이 아니다. 기존 코드와의 충돌 및 이동 비용을 조사하여 필요한 최소 변경만 수행한다.

### 3.2 강제 데이터 계약 (형태는 UPrimaryDataAsset / UDataAsset / DataTable / JSON 중 선택)

| 데이터 | 반드시 담을 정보 | 이번 권역 ↔ 차기 권역 재사용 방법 |
|---|---|---|
| `RegionManifest` | StableRegionID, 부모/인접 권역, 버전, Bounds, 좌표 기준, 월드/레벨 소유권, 생성 Seed | 새 Region 추가 시 기존 ID 및 참조 불변 |
| `WorldGridSpec` | Unreal 기준 좌표 원점, cm↔m 변환, 타일/셀 기준, 고도 기준, 경계 엣지 | 인접 영역의 높이·도로·바이옴 정합 |
| `TerrainProfile` | 높이맵 소스/해시, 타일, 고도 범위, 경사/곡률/수계·침식 파생 정보 | 새 지형을 동일 분석 파이프라인으로 처리 |
| `BiomeProfile` | 고도·경사·수분·토질 분포, PCG Graph/Profile 참조, 에셋 풀, 밀도/LOD | 새 권역은 바이옴 파라미터와 에셋 풀 교체 |
| `RoadNetworkData` | Node/Edge ID, 도로 등급, 폭/경사/커브, 교량/터널 태그, 외곽 연결점 | 권역 경계 도로 연결 유지 |
| `SettlementArchetype` | 수도/농업/숲/항구/호반/산악/소취락 유형, 필지 규칙, 에셋 팔레트 | 동일 생성 도구로 문화권/지형별 차이 구현 |
| `LocationRegistry` | S/H/B/랜드마크 StableID, 경계, 진입로, 참조 Actor/Asset, 완료 상태 | 퀘스트/월드맵/스폰/지역 이동에서 안정적 참조 |
| `HuntingGroundProfile` | 레벨 곡선, Encounter/스폰 후보, Nav/충돌 조건, 몬스터 데이터 참조 | 새 지역의 31+ 사냥터에 같은 데이터 구조 적용 |
| `BossEncounterProfile` | 보스 ID, Arena/집결/리셋 범위, 서버 이벤트/스폰/보상 훅 | 새 보스 종류는 데이터와 능력/AI 구현만 추가 |
| `WorldEdgeContract` | 동·서·남·북 연결점/경계 높이·기울기·수계·도로·바이옴·버전 | 신규 권역 생성 시 경계 이음 기준 |
| `GenerationRecord` | 구역, 생성 패스, 그래프/설정 버전, Seed, 입력 에셋 해시, 수동 수정 보호 목록 | 안전한 부분 재생성 및 회귀 검증 |

**Stable ID 정책:** ID를 에셋 이름 또는 레벨 좌표에 종속시키지 않는다. ID 변경 시 퀘스트/세이브/스폰/월드 마커가 깨질 수 있으므로 마이그레이션 테이블 없이 변경하지 않는다. `SET_*`, `H01..09`, `B01..02`는 이번 프롬프트의 **기획 논리 ID**이며 기존 프로젝트에 공식 ID가 있으면 매핑만 만들고 기존 식별자는 보존한다.

**중요:** `Data Layer`는 액터 그룹/상태 관리용이고, 모든 시스템의 데이터 저장소/지역 식별자로 오용하지 않는다. World Partition은 클라이언트의 공간 스트리밍을 담당하지만 MMO 서버 샤딩/월드 서버 전환을 자동 처리하지 않는다.

### 3.3 지형·도로·정착지·식생 생성의 의존성 그래프

```text
기존 Heightmap / Landscape / 고도 기준 [원본 보존]
    ↓
Terrain Analysis : Height / Slope / Curvature / Watershed / Exclusions
    ↓
Hydrology Plan : 강원·지류·본류·호수·하구 및 강바닥/둔덕
    ↓
Settlement Candidate Validation : 입지 및 필수 장소 안정화
    ↓
Road/Bridge Network : 지역 연결, 경사/하천 회피, 고개·다리
    ↓
Urban Lots / Building Layout : 유형별 필지·건축·랜드마크
    ↓
Biome / Vegetation / Surface Detail : 지역별 PCG 및 수동 아트
    ↓
Gameplay Spatial Anchors : 사냥터/보스/Nav/스폰 후보(위치 계획은 초기부터 병행)
    ↓
HLOD / Streaming / Collision / Package / Profiling
```

변경 영향 추적: 상위 데이터 변경 시 필요한 하위 단계만 `Dirty`로 표시·재생성. 변경하지 않은 8×8km 전체를 매번 다시 생성하지 않는다. 구역/타일/Actor 집합 단위로 롤백 가능해야 한다.

### 3.4 PCG Graph/에셋의 재사용 설계

- Graph를 `PG_Biome_Forest`, `PG_Biome_Meadow`, `PG_Biome_Riverbank`, `PG_Rocks_Cliff`, `PG_Settlement_Lots`, `PG_FarmFields`, `PG_RoadProps`, `PG_HarborProps`와 같이 역할별로 분리하는 안을 **기존 PCG 이름/구조에 매핑**하여 설계한다.
- 공통 Subgraph로 `SlopeMask`, `WaterDistanceMask`, `RoadExclusion`, `SpawnExclusion`, `SettlementReservedZone`, `AssetVariantSelector`, `LODPolicy`, `PlacementValidation` 등을 제공한다. 새 지역 추가 때 공통 그래프를 복사하지 않고 재사용한다.
- 지역 설정은 `BiomeProfile`·`SettlementArchetype`·`AssetPalette` 등을 주입한다. 예: 같은 숲 그래프라도 온대 혼합림/고산 침엽수림에서 수종·밀도·지면 재질이 달라야 한다.
- Seed는 `(WorldSeed, RegionID, GeneratorID, TileID, Revision)`의 **안정적 조합**으로 관리하는 방식을 평가한다. 실제 해시 API·결정성은 구현 환경에서 검증한다. 지역 A 수정으로 지역 B의 생성 결과가 멋대로 변해서는 안 된다.
- World Partition 및 PCG Partitioned/Hierarchical Generation을 에셋 규모에 맞춰 검토한다. 먼 거리 수목·큰 암반과 근거리 Grass를 다른 배치/LOD 정책으로 운용한다.
- 주요 랜드마크와 편집된 건축물은 `ManualOverride/ProtectedActor` 또는 동등한 기존 기능으로 보호. **수동 수정한 장소는 재생성해도 날아가지 않을 것.**
- 필드 보스·NPC는 PCG로 **정적 스폰 후보**를 마련할 수 있지만, 스폰/AI/보상/전투 상태는 게임 서버 권한 시스템이 담당한다.

### 3.5 권역 추가 시 최소한의 변경으로 재사용되는지 증명

**미래 권역의 작은 샘플**(예: 수백 m 정도의 *검증용 비공개 테스트 영역*)을 기존 월드와 충돌하지 않는 곳에 구성하고 다음을 검증한다. 이번 단계에서 Lv.31+ 정착지·사냥터 콘텐츠 전체 제작은 하지 않는다.

1. 새 `RegionManifest`, `BiomeProfile`, `SettlementArchetype`를 **데이터 추가 중심**으로 정의.
2. 공통 Terrain Analysis / PCG / Road / Settlement Tool이 기존 코드를 복사·수정하지 않고 해당 영역을 생성하는지 확인.
3. 월드 경계 샘플에 강·도로·고도·재질·식생이 끊기지 않고 이어지는지 확인.
4. 생성 영역만 부분 재빌드하고 현재 Lv.1~30 지역이 손상되지 않았는지 검증.
5. 결과 및 미지원 항목을 `EXPANSION_PROOF.md`에 기록. **테스트용 후속 지형은 정식 신규 권역으로 보고하지 않는다.**

## 4. 미래 월드 확장: 하나의 월드 유지 vs. 별도 월드 선택 원칙

### 4.1 우선안: 지리적으로 연결되는 지역은 동일 World Partition 월드 확장 검토

- 플레이어가 걸어서/탈것으로 Lv.30 경계에서 다음 권역으로 **로딩 화면 없이 이동**하는 것이 목표인 경우, 현재 Persistent Level/World Partition의 지리적 확장 가능성을 우선 검토한다.
- 확장을 염두에 둔 Landscape 타일/Streaming Proxy/기준 좌표/World Origin/높이맵 소유권을 정리한다. **기존 8km Heightmap에 임의로 새 타일을 붙이면 항상 완벽히 연결된다고 가정하지 않는다.**
- 특히 사용 중인 Landscape 구성이 확장에 제약이 있다면 성급한 재생성을 하지 말고 A) 인접 타일·컴포넌트 확장 B) 더 큰 장기 마스터 월드 그리드 C) 분리 월드 전환의 비용·위험을 비교한다.
- World Partition 셀/Runtime Grid 설정, HLOD, Data Layer, One File Per Actor, 경계 Landscape 재질/Collision/Water/PCG/Navigation 이음 검증을 동반한다.

### 4.2 대안: 별도 Persistent Level / 월드 서버가 필요한 경우

- 월드 물리 규모, 샤딩·서버 인원, 해상 콘텐츠, 월드 구조가 달라 별도 맵이 합리적이면 분리 월드 구성을 선택할 수 있다.
- 이 경우 **World Partition만으로 별도 `.umap`을 동일 공간처럼 자연스럽게 이어주지는 않는다.** 전환 지점, 맵 로딩/월드 전환, 서버 권한·세션·파티/플레이어 상태·퀘스트·네트워크 이전, 사전 로딩 연출을 별도 설계한다.
- 유저가 원하지 않는 갑작스러운 검은 화면이나 로딩 체감이 생기지 않도록 후속 개발 시 설계/프로토타입을 요구한다.
- **현 단계에서 반드시 한 방법으로 확정할 필요는 없지만**, 다음 지역 추가 시 전면 재작업하지 않도록 양 대안의 호환 인터페이스를 제공한다.

### 4.3 강제 World Edge Contract (네 방향 각각 기록)

각 방향마다 다음을 문서/데이터로 저장한다.

| 항목 | 기록 내용 |
|---|---|
| `BoundaryEdgeID` | 방향 N/E/S/W, 유효 구간, 실제 좌표와 높이 기준 |
| `TerrainContinuity` | Height/Gradient/Slope/Material layer weights, 원본 heightmap/tile 버전 |
| `HydrologyPorts` | 강 유입/유출, 하상 높이, 유로 폭·흐름 방향, 연결할 수계 ID |
| `RoadPorts` | 도로 노드/분기, 연결 예정 도로 등급·폭·진행 방향·통행 모델 |
| `BiomeTransition` | 숲/초원/고산/해안 등 바이옴 가중치와 이음 거리 |
| `GameplayGate` | 현 지역 최소 권장 레벨, 퀘스트/안전 구역/몹 경계, 전환 필요 여부 |
| `Validation` | 실제 높이/충돌/네비게이션/시야/스트리밍 테스트 결과 |

**경계 확보 규칙:** 북부 산악 관문, 동부 숲길, 서부 평야길 등 최소 3개 육상 연결 후보와, 남쪽 하천·해안/선박 확장 후보를 유지한다. 지금 구현된 강과 도로는 확장 시 중간에서 갑자기 끊기는 형태가 되지 않도록 다음 구역 쪽으로 연장 의도를 표시한다. 외곽을 반복적인 수직 절벽으로 막거나 아무 이유 없이 전부 바다로 둘러싸지 않는다.

## 5. 현재 8×8km 실제 제작: 지형·수계·도로·마을·환경 요구사항

### 5.1 거시 지형: 원본 유지 + 자연스러운 지역 분화

- 기존 산체/Heightmap은 보존하고, **비파괴 경사 보정·절벽/암석 보강·침식 지형·소규모 계곡/구릉·도로 접합**을 수행한다.
- 산맥→능선→고개→계곡→평야의 연속된 지형적 논리를 유지한다. 현재 화면의 반복적인 작은 언덕과 인공적인 경사, 수변의 평면/기하학적 형태는 검증 후 보정한다.
- 높은 전망대/산길·고원을 **실제로 플레이 가능한 Z축 이동 공간**으로 만든다. 산길 폭, 헤어핀, 고도차, 경사 한계는 현 캐릭터와 탈것 이동값으로 판단한다.
- 동굴/오버행/수직 절벽은 Landscape heightfield로만 표현하기 어렵다면 기존 Cliff Mesh/모듈형 동굴 에셋을 재사용한다. Experimental 기능만으로 전체 월드를 갈아엎지 않는다.

### 5.2 수계: 강·호수·강둑·하상·교량

- 기존 강 수면이 **검토용**이라면 실제 물 표면/물리·Collision/Water Body/강바닥·강둑/수생 식생과 다리 접합을 완성한다.
- 하천은 수원·지류·합류·본류·하구의 고도와 흐름이 일관되어야 하며, 폭·곡률·자갈/모래/진흙 분포에 변화가 있어야 한다.
- 호수는 단순 원/타원형 평면 대신 실제 함몰 지형과 수면·호안 지형과 일치하고, 유입/유출 포트가 설명 가능해야 한다.
- 도로와 다리의 경사/교량 하부 여유/진입로 접합, 캐릭터와 탈것 충돌, 수면 부유·침수 등을 테스트한다.

### 5.3 대도시·마을·취락 생성 규칙

- 건축물 타입·높이·폭·지붕 방향·표면 재료의 다양성과 **건축 양식의 일관성**을 함께 유지한다.
- 대도시는 `지형 적합 입지 → 성채/광장 → 큰 도로 → 구역 → 불규칙 필지 → 건축물 → 생활 소품` 순서. 모든 집을 정렬·격자 복제하지 않는다.
- 산악 마을은 좁은 능선·계단식 터·산길·옹벽, 농촌은 농지·관개·농로, 항구는 수심·부두·창고·길, 숲 마을은 간벌지·숲길 등 **타입별 서로 다른 알고리즘**.
- 건물과 지형 접합부, 출입문 높이, 문·창·지붕 파츠 연결, 실내 진입 가능 건물의 출입/충돌, 길가 소품 배치를 검증한다. 실내 구현은 기존 목표/가용 에셋에 따라 단계화하되 무조건 모든 집에 실내를 요구하지 않는다.
- 월드 전체에 도시 이름만 표시하는 것은 완료 아님. **실제 StaticMesh/LevelInstance/Actor와 통행 가능한 길로 공간이 형성되어야** 장소 구현으로 인정한다.

### 5.4 바이옴·Landscape Material·실제 3D 식생

- 지형이 동일한 녹색 풀 텍스처 하나로 보이지 않도록 풀/마른 풀/흙/자갈/암반/젖은 진흙/모래/낙엽/이끼 등 Layer를 지형·경사·수분·바이옴에 따라 혼합한다.
- Landscape Material과 실제 Grass Mesh는 분리하여 품질 평가하고 색이 서로 어색하지 않게 맞춘다. Macro Color/Texture Variation 및 지형의 대형 색상 패턴도 추가한다.
- Grass Type/Grass Output 또는 적합한 기존 기능으로 짧은 풀·긴 풀·야생화/작은 잡초의 지면 커버를 만들고, PCG/Foliage로 중·대형 수목·관목·고사리·덤불·돌·쓰러진 나무·수변 식생을 구성한다.
- 바이옴 종류: 농경지/초원, 온대 대삼림, 숲-구릉 전이, 호반, 습지, 강변, 해안, 중고산 암반, 높은 능선/눈(실제 온도·고도와 맞을 때). 고정된 사각형 바이옴 경계 금지.
- 마을과 도로, 경작지, 사냥터 전투 공간과 보스 아레나는 **배치 제외/밀도 저감** 마스크. 모든 장소를 같은 확률로 수목으로 뒤덮지 않는다.
- 분포 규칙에 수종 군집·수령/크기·서식 환경을 반영. 가까운 거리의 작은 풀뿐 아니라 중경/원경의 숲 윤곽도 자연스러울 것.
- 서로 다른 Fab/기존 에셋의 건축·식생·재질은 색감, 스타일, 스케일, UV/텍스처 해상도를 검토해 통일. 새로운 유료 에셋은 사용자 승인 없이 구매하지 않는다.

### 5.5 사냥터·보스·세계의 게임플레이 연결

- 9개 사냥터와 2개 보스 공간은 **이동 가능한 세계의 실제 지형 위에 존재**해야 한다. 각 장소마다 1개 이상의 주 접근로, 적절한 대체 접근/퇴각로, 안전 경계, 실제 충돌 및 경사 조건을 검증한다.
- 몬스터 AI 이동은 기존 Navigation/AI 시스템을 우선 사용. World Partition NavMesh는 UE 5.8에서 Experimental이므로 기술 검증 후 채택.
- 월드 기하학/PCG와 게임플레이의 **데이터 계약**을 정의해, 월드를 재생성해도 몬스터 스폰/퀘스트/안전지대가 유효해야 한다.
- Static Foliage를 대규모 Replicated Actor로 만들지 않는다. 동적 게임플레이 오브젝트는 서버 소유권과 관련성(Relevancy), 리스폰·원거리 활성화/비활성화 정책을 가진다.

## 6. 구현 Phase — '지도 후보'가 아닌 실제 장소 완성까지

**원칙:** 8×8km 전체 지형 크기는 계속 유지한다. `모든 장소의 공간 배치 → 대표 구간의 기준 품질 → 전역 고도화`의 균형을 취한다. 대표 구간 하나만 작업하고 나머지를 후보로 둔 채 최종 완료라고 하지 않는다. 각 Phase 완료 후 다음 Phase로 진행할 수 있으나, 하위 시스템에 필요한 고정 계약은 선행 마련한다.

### Phase 0 — 현행 프로젝트 인벤토리/보존/작업 대상 고정

- Project_J/현재 브랜치 확인, Heightmap·Landscape 원본/해시/External Actors 보존 상태 및 자동 복구 방법 기록.
- 현장 스크린샷·기존 장소/후보와 `S01..S09`, `H01..H09`, `B01..B02` 매핑.
- 기존 C++·PCG·에셋·게임플레이 시스템 재사용/신규/수정/보류 목록 작성.
- 성능 타깃 및 도보·탈것·최고 스킬 속도, 테스트 PC 사양은 실제 확인. 정보 부족 시 값 임의 확정 금지.
- **완료:** 대상과 기존 현황을 파일/Actor 기반으로 식별하며, 원본 보존 및 안전한 수정 범위가 확정됨.

### Phase 1 — 8×8km 공간 계획·20곳 전체 실체화 (우선)

- 6개 큰 지역(중앙/남서 농업/동부 숲/서부 호반/남동 항구/북부 산악·고원)을 지형 기반으로 구획. 지형을 정사각형 6등분하지 않는다.
- 필수 S 9곳, H 9곳, B 2곳의 범위(Polygon/Volume), 진입 지점, 최소 토지 형태, 안전/완충 구역, Region 및 레벨을 실제 월드에 등록.
- S 장소는 최소 **실제 건물/성벽·시설 블록아웃+접근로**까지 생성. H/B 장소는 최소 **실제 전투 가능 평면/지형·접근로·주요 장애물**까지 조성.
- 빠진 장소가 '좌표 후보만 있음' 상태로 남지 않도록 목록 검사. 입지 불가능하면 기존 지형을 파괴하지 말고 가까운 적합 지형으로 이동 후 기록.
- **완료:** 20곳 모두 실제 공간과 `StableID/Bounds/입구`가 있고, 편집기에서 각 위치로 이동 가능한 상태. 완성 단계(블록아웃/아트/게임플레이)는 별도 표시.

### Phase 2 — 지형·수계·도로·산길의 구조적 품질 완성

- 기존 고도 데이터 비파괴 유지 아래 주요 경사·산등성이·구릉·절벽 주변의 인공 패턴 완화.
- 산지 수계와 호안·강둑·하상·하구·교량 접합 개선. 임시 파란 강 수면/타원형 호수 검토 후 물 시스템 교체/고도화.
- S/H/B 연결 대로·보조도로·산길·우회로 완성. 끊긴 도로, 물속으로 사라지는 경로, 고도차 충돌을 검출.
- 최소 3곳 고산 전망·산길 경로와 미래 권역 확장 고갯길 노드 구성.
- **완료:** 주요 도시/마을 간에 도보·탈것으로 이동 가능한 연결 그래프, 강·교량과 이동 지형의 접합 검증, 지형 원본 손실 없음.

### Phase 3 — 전역 지표면 재질·바이옴·PCG 식생 시스템

- 공통 Landscape Material과 주요 바이옴, Foliage/PCG Subgraphs 및 Profile 구현.
- 초원/숲/호수/산악/강변/해안 등 대표 샘플 구간에서 시각/성능/재현성을 검증한 후 **8×8km 전역 해당 바이옴에 적용**.
- 지역에 맞는 다양한 나무·관목·꽃·작은 풀·지면 재질·암반·습지 식생. 빈 평야와 반복된 녹색 표면 해결.
- 도로·마을·사냥터와의 제외 마스크 및 재생성 시 수동 보정 보호.
- **완료:** 주요 권역별로 뚜렷한 지면 재질과 중경/원경의 식생 차이가 보이고, 바이옴 전체에 적용된 결과를 재현 가능하며, 성능 기초 측정이 존재.

### Phase 4 — 수도·마을·소취락 9곳의 건축·생활환경 완성

- 수도 S01: 성곽/광장/상업/주거/공방/중심 랜드마크/교통 구조를 실제로 구현. 외곽 진입부에만 건물 몇 채를 세우지 말 것.
- S02~S06의 각기 다른 생활 기능·건축 배치 규칙과 S07~S09 소취락의 고유 용도 확립.
- 건물 기초·도로·지붕·문/창·창고/마당·농지/부두/목책/표지 등 주변 환경과 접합. 건축 에셋 부족·임시 메시 사용은 `ASSET_GAPS`로 남기고 승인 가능 범위에서 대체/조달.
- 마을 접근로, NPC 공간, 상점·퀘스트 훅, 기능별 POI를 배치하되 기존 C++ 계약을 변경하지 않는다.
- **완료:** 9곳 모두 ①실제 배치 ②유형별 개성 ③보행/탈것 동선 ④환경 접합 ⑤근거리/원거리 스크린샷 평가를 통과. 기존 임시 블록아웃만 남은 곳은 미완성 처리.

### Phase 5 — 사냥터 9곳 및 보스 2곳의 공간/콘텐츠 통합

- H01~H09 각각 실제 전투 지형, 진입/퇴각, 스폰 후보/몬스터 분포, 환경 경고, 전투/충돌/Nav 테스트.
- B01/B02 각각 보스 전용 아레나, 장애물/단차/접근로/안전 집결지/리셋 구역 구성. 보스 모델·AI·Ability가 있는 경우 기존 시스템으로 실제 전투 루프 통합.
- 실제 게임플레이 시스템이 없다면 '전투 완성'이라 쓰지 않고 사용자가 보완해야 할 에셋/애니메이션/서버 코드를 문서로 구분. 작동 가능한 기능은 실제 구현할 것.
- **완료:** H/B 각 공간의 플레이 가능성과 인터페이스 검증; AI/스폰/퀘스트/룻은 기능별 `실동작/미구현/검증 불가`로 표시.

### Phase 6 — 고속 이동·원경·스트리밍·성능 최적화 (Phase 2부터 병행)

- World Partition Enable Streaming 확인, Streaming Source와 로딩 반경, Data Layer, HLOD, Nanite/ISMC/HISMC, PCG 결과의 Editor Bake 또는 저장 전략 확인.
- 보행/고속 스킬/최고 속도 탈것으로 **수도 진입, 숲 질주, 굴곡진 강변길, 북부 고갯길, 전망대에서 급회전, 항구 원경**을 검증.
- 식생·건물의 갑작스러운 등장(pop-in), 텍스처 mip 지연, 셰이더/메시 스트리밍 끊김, NPC/몬스터 지역 활성화와 프레임타임을 분리해 측정.
- 예상 선행 로드 거리의 초기 검토식: `D_prefetch >= V_max × (T_load_p95 + T_margin)`; 이는 **이동으로 인한 로드 지연만 고려한 하한 추정**이며, 시야/지형 고도/원경 HLOD/메모리 제약은 별도로 반영한다. 수치를 근거 없이 하드코딩하지 않는다.
- World Partition/PCG/HLOD Editor Builder Commandlet 등 검증된 도구로 필요한 범위만 빌드한다. 실험적 Nanite Foliage/Mesh Terrain은 테스트 브랜치 검증 후 도입한다.
- 목표 PC/해상도/설정과 GPU/CPU/RAM/VRAM 예산을 명시하고 `Unreal Insights`, `stat unit`, GPU profiler, World Partition/PCG 디버그 등을 활용.
- **완료:** 실제 이동 테스트 로그/프레임타임/메모리/팝인 문제 목록과 수정 후 재측정. 테스트 없이 '60FPS/팝인 없음'이라고 보고하지 않음.

### Phase 7 — 다음 권역 확장성 검증 및 회귀 테스트

- 신규 `RegionManifest`/`BiomeProfile`을 만들어 **검증용 새 영역**에서 공통 PCG/도로/정착지 구성 요소 재사용 시연.
- 기존 스타팅 월드 Edge Contract와 인접 높이·도로·수계·바이옴 연결 시험, 관련 Landscape/데이터 손상 없이 롤백.
- 정착지/사냥터/보스의 ID와 외부 참조, 프로젝트 저장/재시작·패키징·멀티플레이 기초 테스트.
- `World Partition의 동일 월드 확장`과 `별도 월드 전환`의 확장 설계 의사결정 문서 작성.
- **완료:** 기존 8×8km를 재작성하지 않고 새로운 Region 설정을 입력해 최소 샘플을 만들 수 있으며, 경계·이동·데이터·복원 테스트 결과가 있음.

### Phase 8 — 최종 전역 QA·납품

- 모든 20개 핵심 장소의 레벨 디자인·외관·통행·환경/물·스폰/게임플레이 상태 종합 검사.
- 지도 각 권역의 **수직 탑뷰(권역/시설 ID 오버레이는 별도)**와 각 지역의 플레이어 시점/중경/전망대 원경 스크린샷 제출.
- 빌드, 에디터 재시작, PIE/Standalone/패키지, 8×8km 횡단, 물/도시/산길 통행, 팝인/프레임타임, 필드보스 다수인원 상황(가능 범위) 검사.
- 나중에 재현 가능한 빌드 도구/파라미터/Seed/GenerationRecord/사용 에셋 목록 정리.
- **완료:** 제출 체크리스트 충족 시에만 **'시작 권역 환경 완성'**이라고 표기. 기능 미구현은 별도로 남기며, 자동 생성된 아트가 AAA 수준임을 근거 없이 선언하지 않는다.

## 7. 측정 가능하고 재현 가능한 완료 판정(Definition of Done)

### 7.1 위치별 등급 관리

장소 각각을 다음 상태로 기록:
- `PLANNED`: 좌표 후보·설명만 존재
- `SPATIAL_BLOCKOUT`: 실제 지형과 공간·범위·입구/출구 존재
- `ENVIRONMENT_PASS`: 지표면·식생·도로·건축·수변이 주요 시점에서 일관됨
- `GAMEPLAY_READY`: 충돌·이동·스폰/안전 구역·기본 게임플레이 계약 검증
- `PERF_VERIFIED`: 대상 PC와 이동 조건에서 성능·스트리밍/팝인 테스트 완료

사용자에게 '완성'이라 말하려면 해당 범위의 성공 기준을 명시할 것. 장소가 `PLANNED`만 되어 있다면 산출물 수량에 포함하지 않는다. `GAMEPLAY_READY`는 전투 전체가 구현됐다는 뜻이 아닐 수 있으므로 **전투/퀘스트/네트워크 검증 여부를 각기 표기**한다.

### 7.2 최소 현장 검증

1. **좌표/규모:** 8×8km 실제 공간, 높이맵 원본 해시 동일, 높이차·Z축/산길 이동 테스트.
2. **장소:** S01~S09, H01~H09, B01~B02 각각의 `StableID, Actor/Asset 경로, 월드 좌표, 접근로, 스크린샷, 구현 등급` 보유.
3. **도시/마을:** 동일 주택 반복·길과 건물 충돌·문/기초 공중 부유·지붕 겹침·단조로운 격자 여부 체크.
4. **수계/환경:** 강/호수/하구 지형 연결, 수면·강둑 높이 및 경사, 실제 3D 식생과 지면 재질의 다양화 검증.
5. **월드 연결:** 주요 도로망에 S/H/B 위치 접근 가능; 정착지 사이 도보·탈것 동선; 보스 지역 안전 우회로 존재.
6. **스트리밍:** 움직임 속도별 로그와 동일 카메라 지점 Before/After 스크린샷, CPU/GPU 프레임타임·메모리 사용량.
7. **재사용:** 서로 다른 2개 바이옴, 2개 정착지 유형, 다음 Region 샘플을 **설정 교체만으로 동일 도구가 처리하는지** 확인.
8. **회귀:** 원본 Heightmap·기존 게임플레이·Existing Asset 참조·기존 저장/빌드/패키지의 호환성.

### 7.3 시각 검증 관점

- **탑뷰:** 권역 구조, 도시/마을 분포, 산맥·호수·숲 밀도, 도로 연결, 외곽 확장 후보.
- **사선 3/4 뷰:** 2~3km 지형 원경, 산길·교량·성곽과 자연환경의 관계.
- **플레이어 눈높이:** 지면 텍스처 반복, Grass/쓰레기 소품, 도로/벽/문/관목 접합.
- **고속 이동:** 수목·건물의 LOD/HLOD 전환, 텍스처 팝인, 스터터, CPU/메모리 경고.
- **전투 시점:** 다수 적·광역 스킬·엄폐·AI 내비게이션·카메라 공간 확보.

## 8. 출력 파일 및 보고 계약

프로젝트 내부 `Docs/WorldGen/`를 기존 문서 위치에 맞춰 생성 또는 갱신. 기존 파일 덮어쓰기 전에 변경점을 비교한다.

```text
Docs/WorldGen/
  00_BASELINE.md                       기존 Heightmap/UE/브랜치/월드/스냅샷
  01_EXISTING_TO_TARGET_MAPPING.csv    기존 장소/에셋 ↔ S/H/B 대응표
  02_ASSET_REUSE.md                    기존 건축·식생·머티리얼·AI 재사용표
  03_IMPLEMENTATION_STATUS.md          Phase 및 장소별 상태표
  04_WORLD_LAYOUT.md                   8×8km 지역/도로/하천/연결 구조
  05_WORLD_ARCHITECTURE.md             재사용 데이터 계약/PCG/에디터 자동화
  06_WORLD_EDGE_CONTRACT.md            네 방향 외곽 확장 계약/높이/도로/물
  07_GAMEPLAY_SPATIAL_INTEGRATION.md   사냥터·보스·Nav·서버·퀘스트 훅
  08_PERFORMANCE_REPORT.md             이동별 실제 성능/팝인/메모리
  09_EXPANSION_PROOF.md                신규 Region 데이터 기반 샘플 검증
  10_FINAL_ACCEPTANCE.md               전체 20장소+월드 품질 최종 체크리스트
  WORK_CONTINUATION.md                 컨텍스트/세션이 바뀔 때 재개 위치
```

`WORK_CONTINUATION.md`에는 다음 내용을 **매 주요 단계 종료 시 갱신**한다.
- 현재 Git 브랜치/커밋 또는 변경 파일 및 미커밋 상태
- 마지막으로 실제 완료/검증한 단계와 장소 ID
- 코드/PCG/레벨/지형·World Partition 상태
- 시각 검증 스크린샷 경로/카메라 위치, 수행한 테스트 명령 및 결과
- 실패·오류·미검증 사항 및 해결 방법
- 다음에 실행할 구체적인 3~5개 작업과 선행 조건

### 매 작업 종료 시 채팅 보고 형식(짧지만 증거 기반)

```text
[현재 상태] Phase X / S __개 · H __개 · B __개: PLAN / BLOCKOUT / ART / GAMEPLAY / PERF 단계별 수량
[실제 변경] 파일/에셋/Actor/PCG Graph 경로, 생성/수정 결과
[현장 검증] UE 에디터/PIE/Standalone/빌드/패키지 중 무엇을 확인했는지
[시각 검증] 특정 장소의 탑뷰·플레이어뷰·Before/After 스크린샷 경로
[문제/미완료] 근거/영향 범위, 선택 필요 항목
[다음 작업] 실제 구현을 계속하기 위한 순서와 이유
```

**작업 종료/중단 정책:** 도구 오류·컨텍스트·시간 제약으로 중단하면 구현한 부분을 정확히 기록하고 재개 정보를 남긴다. 단순히 'Phase 1 완료'라고 표시하지 않는다. 직접 구현할 수 없는 툴 기능은 불가능한 이유와 대체 구현을 안내한다. 외부 권한/구매/파괴적 파일 변경 없이 가능한 작업은 계속 진행한다.

## 9. 변경 안전성 / 게임플레이 보존 / 서버 확장

- 공급자 원본(외부 에셋 원본)은 직접 수정하지 말고 **프로젝트 내부의 별도 Material Instance, Blueprint 자식, 데이터 에셋**으로 차이를 관리한다.
- 기존 캐릭터, 이동/탈것, 공격 판정, 카메라, Nav, NPC/몬스터, 퀘스트/아이템/루팅, 네트워크 등 게임플레이 API 계약을 감사하고, 변경 필요 시 인터페이스 마이그레이션 및 회귀 테스트를 준비.
- 현재 단일 World Partition 맵 구성과 앞으로의 Dedicated Server/멀티플레이 스케일링은 별개 설계 항목. 정적 식생을 개별 서버 Replicated Actor로 생성하지 않으며, 동적 전투·NPC·보스는 서버 권한/관심 영역 정책 적용.
- 대규모 NavMesh, Nanite Foliage, 일부 Mesh Terrain 기능은 실험적/버전 의존성을 검토하고 격리된 샘플에서 테스트. 안전한 기본 경로를 유지.
- 파일·에셋 Rename/Move/Delete, 기존 Heightmap 파괴적 수정, 결제/다운로드 라이선스 수락은 사전 승인이 필요. 기존 Git 작업 상태를 강제로 정리하지 말 것.
- 단계별 개선으로 잠시 성능이 저하될 수 있다면 임시 상태임을 명시하고 최종 예산을 지키기 위한 기술적 해결책을 같이 진행.

## 10. Codex가 이 프롬프트를 받자마자 해야 할 일

1. `Project_J` 현재 작업 브랜치와 `WorldGen_Prompt_v3.md`, 첨부 `References/`, `ZONE_LAYOUT_LV1_30.json`, 기존 레벨·Heightmap 확인.
2. `S01..S09`, `H01..H09`, `B01..B02`의 실제 구현/후보/미구현 상태를 **객관적인 파일 및 액터 기반**으로 매핑.
3. 필수 계약(`StableID/RegionManifest/BiomeProfile/Edge Contract/GenerationRecord`)을 기존 코드와 최소 변경으로 연결할 설계 작성.
4. **Phase 1부터 실제 구현 착수:** 이미 구현된 건 보존하고 빈 장소부터 공간/접근로/블록아웃 구축.
5. 비파괴 작업을 진행하며 매 단계 에디터 검증/스크린샷/성능/진행상태 문서화.
6. 대표 구간 품질을 높이면서도 전체 20곳의 구현 목표를 절대 잊지 않도록 Status Tracker를 갱신.
7. 안전 문제 또는 권한이 필요한 작업만 사용자에게 요청. 나머지는 작업을 진행한다.

**최종 목표 한 문장:** `Project_J`의 기존 8×8km 높이 데이터와 게임플레이를 안전하게 보존하면서, Lv.1~30 구간에서 실제로 탐험·이동·전투 가능한 수도·마을·사냥터·필드 보스·고밀도 자연환경을 완성하고, 이후 Lv.31~100 새로운 지역은 공통 데이터와 생성 시스템을 재사용해 확장할 수 있도록 만든다.
