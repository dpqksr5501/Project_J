# 이동 중 180도 Turn 선택과 요청 수명

2026-10-06. `codex/locomotion-facing-transitions`에서 구현한다. Reface·Spin을 새 검색 후보로 추가하지 않는다. 기존 Start·Stop·Pivot·점프·낙하·착지·stationary TIP의 direct Blend Stack 소유권을 유지한다.

## 범위와 에셋의 이동 계약

확인한 `M_Neutral_Run_Turn_L_180_Lfoot`와 `M_Neutral_Run_Turn_R_180_Rfoot`의 로컬 루트 샘플은 약 ±180도 몸 회전과 이동 경로 반전을 함께 나타낸다. 세계 이동 경로를 유지하면서 몸만 회전하는 상황이나 뒤로 달리던 자세에 이 전진 Turn을 강제로 적용하지 않는다. 루트 샘플은 최종 리타깃·발 접지의 시각 검증을 대신하지 않는다.

| 상황 | 처리 |
| --- | --- |
| OTM Run에서 마우스 회전으로 전진 경로와 몸 목표가 크게 반전 | 기존 Run Turn PSD 검색 |
| OTM Run에서 반대 키 입력 | 기존 Turn 선택을 유지하고 큰 반전의 수명·검색 edge 보완 |
| Strafe Run에서 마우스 회전으로 몸 목표와 전진 경로가 함께 크게 반전 | 선택적 Combat Run Turn PSD 검색 |
| Strafe에서 반대 키 입력, 몸 목표 유지 | 기존 Pivot 또는 Cycle 정책 |
| Strafe의 작은 회전, 옆/뒤로 달리기, 세계 경로를 유지하는 몸 회전 | 기존 Dynamic Cycle |
| OTM↔Strafe 전환 자체 | 새 180도 Turn 요청을 만들지 않음; 기존 trajectory facing 예측 유지 |

추가 180도 수명 정책은 로컬 Run만 대상으로 한다. 기존 OTM의 45·90·135·180도 선택과 Sprint Turn 경로는 유지한다. 원격의 미복제 controller yaw를 추정하거나 새 RPC·복제 필드를 만들지 않는다.

## 구조

`FProject_JMovingTurnPolicy`는 값만 받는 작은 수명 정책이다. 기존 locomotion component 업데이트에서 한 번 평가하며 새 Tick, montage, gameplay state, 에셋 로드, trajectory 전체 순회가 없다.

현재 snapshot의 velocity·world input·actor facing과 mode별 목표를 사용한다. OTM 목표는 이동 의도, Strafe 목표는 controller desired yaw다. one-shot에 쓰이는 `DesiredFacingYaw`를 Strafe camera-facing 목표로 재사용하지 않는다. policy가 보관하는 entry target은 수명 중 목표 급변을 판단하는 기준이고, MM에 이전 snapshot이나 고정 목표를 공급하지 않는다.

진입 조건은 다음과 같다.

- 로컬·OnFoot·물리적 지상·Run·Locomotion이며 이동 입력과 최소 속도가 있다.
- Start·Pivot·TIP·착지·점프·낙하·공격·구르기·피격·montage·root motion의 소유 중이 아니다.
- 몸과 목표 차이 150도 이상, 현재 속도와 새 이동 방향 차이 135도 이상이다.
- 현재 속도와 현재 몸 방향, 새 이동 방향과 목표 몸 방향은 각각 45도 이내다. 전진 Turn 에셋의 입력/출력 동작과 맞추기 위한 조건이다.
- 해당 owner에서 정렬된 이동을 먼저 관측했다. 모드 전환이나 일회성 동작 종료 때 남은 큰 각도로 재진입하지 않는다.

진입 후 velocity가 새 방향으로 바뀌어도 같은 Turn window는 유지한다. 목표 정렬, 입력/목표의 부조화, entry target에서 60도 넘는 목표 변경, 상위 동작 또는 0.75초 상한에서 종료한다. 0.10초 cooldown과 정렬 관측 후 re-arm을 사용한다. 같은 큰 각도로 timeout 뒤 계속 새 요청을 만들지 않는다. ±180도 부호는 별도 좌/우 상태를 만들지 않고 MM의 trajectory·pose-history 후보 비교에 맡긴다.

Combat profile의 `StrafeFacingRedirectEntryAngle` 기본은 150도다. 기존 DA에 저장된 30도 등 작은 값도 런타임에서 150도 이상으로 제한한다. exit angle 기본 5도와 기존 opt-out은 유지하고 잘못된 숫자는 유한한 기본값으로 대체한다. 이 제한은 Turn 진입에 적용하며, 작은 회전의 기존 future-facing 예측을 끄지 않는다.

`bMovingTurn180`은 selection key/snapshot으로 전달하는 로컬 의미다. Cycle뿐 아니라 기존 OTM Turn 내부에서 큰 반전이 시작되는 경우에도 한 번의 검색 edge를 구분한다. Strafe Turn PSD는 이 자격이 있을 때만 열리고, 비어 있으면 같은 Combat DA의 Dynamic Cycle로 돌아간다. 오래된 SettledCycle 플래그, OTM PSD, idle을 대신 사용하지 않는다. OTM의 자격 있는 큰 Turn은 명시적 Asset Set 선택을 사용해 legacy Chooser가 Cycle/Idle로 덮어쓰지 않게 한다.

기존 proxy의 최신 snapshot 교체·검색 실행 확인·미실행 요청 보관·군중 예산 계약을 사용한다. entry에서만 force request를 게시한다. 숨김 캐릭터를 추가로 깨우거나 매 프레임 force search하지 않는다. Cycle↔Turn database interrupt는 두 모드 모두 continuing pose를 유지하는 기존 방식으로 적용한다. 요청이 취소되면 기존 phase minimum hold가 해당 큰 Turn을 부활시키지 못한다.

## 데이터 연결

이번 요청은 코드 작업이므로 PSD·DA·ABP·레벨을 저장하지 않았다.

- OTM: 기존 `DA_Player_Locomotion.RunDatabases.TurnRedirect`의 `PSD_Run_Turn`을 유지한다.
- Strafe: `PSS_Combat`을 사용하는 180도 전용 PSD를 만들고 `DA_Player_Combat_Strafe.RunDatabases.TurnRedirect`에 연결한다.
- 후보는 `M_Neutral_Run_Turn_L_180_Lfoot`, `...L_180_Rfoot`, `...R_180_Lfoot`, `...R_180_Rfoot` 네 개다. 기존 `PSD_Combat_Run_Turn`은 45/90/135도도 포함하므로 그대로 연결하면 180도 전용 후보 집합이 되지 않는다.
- Strafe Sprint에 Run Turn을 새로 연결하지 않는다. 새 window는 Run 전용이다.
- PSD별 schema/발 특징·root motion 처리·retarget 상태는 기존 authored 계약을 유지하고 MM이 pose/time을 선택하게 한다. 애니메이션을 0초부터 강제 재생하지 않는다.

MM 내부 Blend Stack, Steering, Offset Root Bone을 이번 코드 작업에서 변경하지 않았다. 현재 root rotation Release 정책의 영향, capsule 회전과 시각 루트 회전의 중복, 발 미끄러짐은 데이터 연결 후 실제 MM asset/time·최종 포즈로 확인해야 한다. 코드 검증 통과를 자연스러움 개선의 완료로 간주하지 않는다.

## 에디터 재현용 진단

DA 연결 후 Turn이 보이지 않는 문제를 분리하기 위해 `p.ProjectJ.MovingTurnTrace`를 추가했다. CVar 기본은 0이고, 현재 `Config/DefaultEngine.ini`의 `[SystemSettingsEditor]`에 임시로 2를 설정해 에디터 PIE에서 자동 기록한다. 로컬 PlayerController의 캐릭터만 대상으로 한다. 게임용 검색 조건·throttle·snapshot·에셋 선택을 변경하지 않는다. 재현 분석 후 임시 설정을 제거한다.

에디터에서 PIE 실행 후 Shift 없이 OTM/Strafe의 W 유지 + 좌/우 180도 카메라 반전을 각각 2~3회 재현하고 PIE를 종료한다. `Saved/Logs/Project_J.log`의 `MovingTurnTrace`를 분석한다. 에디터를 닫거나 재시작하기 전에 완료됐다고 알려주면 원본 로그를 별도로 보존할 수 있다.

- `Stage=Eligibility`: 실행 중인 실제 AssetSet·TurnPSD·Schema·후보 수, mode/gait/ground 상태, speed, actor/target/velocity/input yaw, Facing·Path·OldForward·NewForward 각도, Guard/Reason, armed/active 상태.
- `Stage=Selection`: snapshot의 최종 phase·Turn180·selection revision, 실제 요청 PSD, MM enabled/update/force, one-shot override/presentation과 검색 예산.
- `Stage=Result` / `Stage=Node`: 실제 MM 결과의 PSD·에셋·재생 시점·continuing·elapsed, 적용 PSD와 캐시된 노드 가중치. cached result는 최종 출력 기여의 증거가 아니므로 node/weight를 함께 본다.
- `Stage=Reselect`: 무장한 request가 엔진 검색 타이머를 실제로 reset했는지 `Executed`로 기록한다. 에셋이 바뀌지 않아도 검색은 실행될 수 있으며, 비활성 노드는 `Executed=0`으로 남는다.

Reason의 `NotArmed`는 owner에서 먼저 정렬된 Run을 관측하지 못한 경우, `FacingBelowEntry`는 몸-목표 차이가 150도 미만인 경우, `PathBelow135`는 이동 경로 반전이 작은 경우다. `OldTravelNotForward`/`NewTravelNotForward`는 전진 Turn 에셋의 이동 계약과 맞지 않는 경우다. `Ineligible`이면 Guard로 Start·Land·Sprint·공격·montage 등의 우선 소유자를 확인한다. 잘못된 슬롯 할당은 AssetSet/TurnPSD에서, 검색 결과 유지와 실제 graph 비활성은 Selection/Result/Reselect에서 구분한다.

### 10:53 PIE 진단 결과

사용자 재현 로그를 `Saved/Validation/MovingTurnTrace_20261006/PIE_1053`에 보존했다. OTM 1회·Strafe 7회 모두 실제 검색 실행과 180도 Turn 에셋 선택을 확인했다. 그러나 8회 모두 반전 감속으로 속도가 180 미만이 되면서 `Guard=Speed`로 해제됐다. 활성 시간은 0.008~0.025초이고 다음 업데이트에서 Cycle 검색으로 복귀했다. 진입 속도 조건을 활성 유지에도 적용한 구현이 조기 해제의 원인이다. MM 내부 블렌드의 잔여 기여와 최종 시각 자연스러움은 이 결과만으로 판단하지 않는다.

다음 보완은 진입 조건과 활성 유지 조건을 분리해 입력을 유지한 경로 반전의 일시 감속을 허용하는 것이다. 정지 입력·상태 소유권 변경·목표 변경·시간 상한은 계속 취소 조건으로 유지하고, 에셋 전체 강제 재생으로 바꾸지 않는다. 현재 사용자 연결 Combat Turn의 실제 Schema는 `PSS_Player`이며 기존 Combat Cycle의 `PSS_Combat`과 다르다. 검색은 성공했으므로 이번 조기 해제의 원인으로 간주하지 않으며, Combat용 데이터 구성 일관성은 별도로 확인한다. 이 진단 시점에는 동작 코드를 추가 수정하지 않았다.

### 사용자 보완과 큰 반전의 범위

사용자는 이후 Combat Turn의 PSS를 수정했다고 알려줬으며, 외부 State Controller Blend Stack에는 제자리 회전과 대각 점프용 Steering이 있다고 확인했다. 프로젝트 전체에 Steering이 없다는 뜻으로 이전 MM 내부 그래프 관찰을 확대 해석하면 안 된다. 외부 Blend Stack과 MM 내부 Blend Stack은 별도 경로이므로, 외부 Steering의 연결·alpha·TargetOrientation·현재 에셋/시간 입력을 사진으로 확인한 뒤 이동 MM Turn의 보정 경로를 결정한다.

개선 대상은 OTM의 키보드 큰 반전, OTM/Strafe의 이동 경로를 반전시키는 마우스 큰 회전이다. 일반적인 작은 회전의 기존 Cycle/Chooser 동작과 Strafe 키보드 Pivot은 유지한다. OTM의 기존 45/90/135/180 후보를 삭제해 분리하지 않고, 큰 반전 조건과 전용 후보 슬롯을 선택 경계로 사용하는 설계가 적절하다. 전용 후보 슬롯은 기존 TurnRedirect에 대한 선택적 확장이며 아직 구현하지 않았다. 큰 반전 중에는 선택 결과를 기존 Chooser가 다시 덮지 않도록 현재 보호를 유지한다.

190도 과회전도 검증 범위다. 최종 yaw의 +190과 -170은 같은 방향이지만, 이미 시작한 오른쪽 Turn의 연속성과 새 왼쪽 반전은 다르다. 최신 목표 yaw는 계속 교체하면서 짧은 반전 구간의 회전 방향 의도만 보존하고, ±180 경계에서 즉시 반대 Turn 재진입이 생기지 않도록 한다. 한 업데이트에서 180도 이상 이동한 방향 의도는 정규화된 시작/종료 yaw만으로 복구할 수 없으므로 실제 처리된 look 회전 변화량도 필요한지 검토한다. LookAxis 원시 값은 감도/컨트롤러 처리 전 값이므로 그대로 각도로 사용하지 않는다. 별도 190도 에셋이나 한 에셋 전체 강제 재생을 요구하는 설계는 아니다.

후속 수명 수정에서는 component의 eligibility뿐 아니라 `FProject_JLocomotionContextBuilder::ResolvePhaseFamily()`의 TurnMinSpeed 재검사도 함께 다뤄야 한다. 정책이 active여도 phase가 속도 조건으로 Cycle이 되는 우회 경로를 남기면 안 된다. 현재 큰 반전 판정은 로컬 입력 소유자 중심이므로 원격 동등성은 아직 완료되지 않았다.

MMORPG 비교 자료로 [검은사막 개발사 GDC 2018 발표](https://s1.pearlcdn.com/pearlabyss/publications/%5BPEARLABYSS%5D_GDC2018_Taking_MMO_Development_to_the_Next_Level.pdf)의 애니메이션 다층 구성·동적 로딩·거리별 IK/물리 제한, [Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine)의 thread-safe 계산·무기 linked layer, [City Sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/city-sample-project-unreal-engine-demonstration)의 근거리 skeletal/원거리 vertex animation, [Animation Budget Allocator](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-budget-allocator-in-unreal-engine)의 중요도 기반 갱신 예산을 확인했다. 검은사막 발표를 MM 구현의 증거로, Lyra/City Sample을 MMORPG 완성 템플릿으로 해석하지 않는다. [motionmatchingreplicated](https://github.com/UmutFarukDilli/motionmatchingreplicated)는 사용자 멀티플레이 비교 자료지만 작성자가 dedicated server를 확인하지 않았다고 명시하고 Smooth Sync 의존·Always Relevant 사용을 설명하므로 대규모 MMO 정책을 그대로 가져오지 않는다.

직접 `UnrealBuildTool.exe`로 Editor/Game Win64 Development 빌드를 성공했다. 진단 추가 후 최종 관련 자동화는 **29개 성공, 경고·실패·미실행·실행 중 0**이다. `TraceReadOnly`는 진단 조회 전후의 판정과 재진입 준비 상태가 같음을 검사한다. [검증 기록](Moving_Turn_180_Validation_2026-10-06.json)의 `diagnostic_validation`에 현재 소스·설정 hash, 빌드 결과, 테스트별 결과, 원본 로그/report 경로를 보존한다. 최상위 28개 결과와 hash는 진단 추가 전 구현의 기록이다.

신규 `ProjectJ.MovingTurn` 테스트는 양 방향과 두 모드의 기하 조건, 작은 회전·키보드 반전·backpedal·yaw wrap 제외, 30/60/120fps 수명, timeout·interrupt·mode handoff·재진입, phase priority와 검색 edge를 검사한다. 기존 StrafeFacingRedirect 회귀는 실제 component의 geometry gate와 데이터 fallback, OTM의 interrupt·동일 phase 재검색 edge·취소 후 최소 hold 방지·Run/Sprint·ownership 경계를 검사하도록 갱신했다. 기존 네 방향 Pivot·연속 반전, Land 복귀·Start episode·one-shot mode continuity, 실제 엔진 검색·nested graph·군중 worker 예산, trajectory history/future facing, mount/Strafe 정책 회귀도 포함했다.

PIE에서는 다음 순서로 확인한다.

1. Run W 유지 + 마우스 좌/우 약 180도 회전: OTM/Strafe 각각 실제 Turn asset/time과 Cycle 복귀를 확인한다.
2. OTM의 W↔S·A↔D, Strafe의 기존 네 방향 Pivot을 확인한다.
3. Strafe S 유지·작은 마우스 회전·옆/뒤 이동에서는 Turn이 끼어들지 않는지 확인한다.
4. Start·Land 중 회전, 반복 TAB, 정지, 공격·구르기·피격·mount 전환에서 중복 one-shot/Turn이 없는지 확인한다.
5. 2인 PIE의 원격 모습과 거리/숨김 예산을 확인한다. 새 로컬 PSD 경로의 원격 시각 동등성을 자동으로 보장하지 않는다.
