# Project J 독립 기술 감사와 후속 검증 자료

첨부 `점검.md`를 검토한 2026-11-23 초기 감사와 이후 단계별 수정·검증 이력이다. 첫 단계는 코드 읽기와 외부 자료 수집이었다. 당시 채집·필드 보스 보상, 인벤토리·영속성, 던전 입장·복귀에서 플레이어에게 결과가 전달되기까지의 간극을 우선 조사 대상으로 기록했다. P0은 권위·보상·진행, P1은 세션·수명·실행 연결, P2는 측정에 따른 최적화와 제작 비용을 가리킨다.

초기 발견 사항은 당시 상태다. 같은 문서의 후속 절에 적용·회귀 조건을 남겼으며, 11월 24일의 단계별 검증과 200인 서버 후속 진단을 포함한 현재 판정은 [독립 기술 감사 후속 현황](Project_J_MMO_Audit_Followup_2026-11-24.md)에 연결했다.

## 확인 범위가 제한된 항목

- **손 IK 스레드 경계.** 두 워커 가능 노드가 `UProject_JRetargetAnimInstance`의 값을 읽는 것은 확인했다. `GuidedHandIK`은 입력 포즈 스냅샷을, `HandContactGoals`는 그 값과 손목 타깃·알파 등을 함께 읽는다. 설치 엔진 `AnimInstanceProxy.cpp`에서는 같은 인스턴스의 `NativeThreadSafeUpdateAnimation`이 그래프 업데이트보다 먼저 호출되고, 프로젝트도 손목 타깃 일부를 이 함수에서 작성한다. UObject 접근 사실만으로 데이터 경쟁을 확정할 수 없다. 게임 스레드 캡처와 워커 파생값의 writer, 링크드·포스트 프로세스 인스턴스 수명, 프레임 동일성을 확인한 뒤 기존 `FProject_JRetargetAnimInstanceProxy`의 데이터 흐름을 검토할 수 있다. [GuidedHandIK](../../../Source/Project_JCharacter/Private/Animation/Project_JAnimNode_GuidedHandIK.cpp#L26), [HandContactGoals](../../../Source/Project_JCharacter/Private/Animation/Project_JAnimNode_HandContactGoals.cpp#L24), [RetargetAnimInstance](../../../Source/Project_JCharacter/Private/Animation/Project_JRetargetAnimInstance.cpp#L555), [Proxy](../../../Source/Project_JCharacter/Private/Animation/Project_JRetargetAnimInstanceProxy.cpp#L35)
- **근접 SSR·AoE·투사체·CC.** 근접 피해 적용, AoE 후보 검사, 투사체 효과 발행에 공통 아군·사망·무적 판정이 보이지 않는다. AoE는 기하·시야 검사 후 결과 배열을 채우며 생산 C++ 호출은 찾지 못했다. 투사체 또한 호출 가능한 진입점과 효과 적용 본문은 있으나 활성 스킬 연결은 미확인이다. 스킬 DA/GE의 개별 제한이 적용될 수 있으므로 아군 오폭과 무적 피해는 현상 재현 전까지 결함 후보로 둔다. CC 자체는 무적 인자를 받을 수 있다. [근접 적용](../../../Source/Project_JCharacter/Private/Components/Project_JCombatHitValidationComponent.cpp#L972), [AoE](../../../Source/Project_JCharacter/Private/Components/Project_JCombatHitValidationComponent.cpp#L1211), [투사체](../../../Source/Project_JCharacter/Private/Combat/Project_JProjectileManagerSubsystem.cpp#L59), [CC](../../../Source/Project_JGAS/Private/Project_JCCResistanceComponent.cpp#L13)

[NPCCharacter](../../../Source/Project_JCharacter/Private/Project_JNPCCharacter.cpp#L42), [WorldEncounter](../../../Source/Project_J/World/Project_JWorldEncounter.cpp#L169)
- **UI·오디오·전환.** HUD의 ESC는 HUD 쪽 최상위 창을 닫고 서브시스템에 반영한다. 컷신·메뉴 취소·월드 정리는 별도 진입이며, `GameInstanceSubsystem` 스택은 로컬 사용자별 키가 없다. 일반 단일 로컬 플레이의 ESC 회귀는 확인되지 않았다. 오디오의 예산 래퍼는 Dedicated Server를 제외하고 월드 정리를 구독하지만, 활성 보이스 수는 피치나 실제 종료 대신 사운드 길이를 상한으로 자른 타이머에서 해제한다. 생산 C++ 호출자가 확인되지 않아 BP 연결과 실사용 보이스는 미확인이다. - **채집과 생활 권위.** 상호작용은 배치한 노드에서 시작하고, 개인·공용 모드 모두 기존 영속 아이템·퀘스트 커밋으로 처리한다. 수락, 커밋, 미반영 확인, 결과 불명 상태를 구분한다. 개인 상태는 월드에서 노드와 캐릭터 ID로 분리하고 슬롯 수와 회수 작업을 제한한다. Tier 1은 기존 작동을 유지하는 기본값이며 상위 등급은 서버 인벤토리의 사용 가능한 도구 정의로 확인한다. 독립 채집 RPC는 실제 월드 상호작용으로 유도한다. 라이브 서버에서의 영속 프로필 연결과 개인 쿨다운 UI는 별도 검증이 필요하다. ## 로컬 백엔드 재시작과 다른 채널 복귀

- **PostgreSQL 우편 수령.** 우편 잠금, 인벤토리 소유권과 슬롯, 골드 출처와 복식 원장, 영수증을 한 트랜잭션으로 처리한다. 가방이 찼거나 세션이 교체됐으면 수령을 거절한다. 거래소 판매대금은 escrow, 필드 보스 골드는 mint를 사용한다. PGlite에서 가방 부족, 다른 캐릭터, 세션 교체, 양쪽 원장과 재개방 회귀를 확인했다. [마이그레이션](../../../Infra/migrations/005_durable_mail_claims.sql), [SQL 검증](../../../Infra/scripts/check-mmo-commands.mjs)
- **우편함 조회.** 현재 DB 세대의 캐릭터만 미수령 우편을 조회하고, 생성 시각과 우편 ID로 정렬해 한 번에 최대 100건을 읽는다. 실제 Nakama HTTP에서 같은 시각에 발행된 두 우편을 한 건씩 읽어 순회했고, 재시작 후에는 이미 수령한 우편을 제외한 골드 우편 한 건이 남아 있었다. [RPC](../../../Infra/nakama/modules/project_j_mmo.js), [실행기](../../../Infra/scripts/test-local-native-backend.ps1)
- **실제 Nakama와 Unreal 통신.** Docker 설치 없이 공식 Windows용 Nakama 3.25.0과 PostgreSQL 16.16을 임시 경로에서 실행했다. Unreal 서비스 포트는 Runtime HTTP 키를 Basic 헤더로 전달하고 Nakama의 `unwrap` 형식을 사용한다. 수정 전 RPC가 정상 세션 번호를 거절하던 정규식도 고쳤다. Unreal이 발행한 우편 수령으로 아이템 3개가 SQL의 `CHAR_INV`에 들어갔다. Nakama와 PostgreSQL을 모두 재시작한 뒤 같은 키의 영수증을 다시 읽었고, 다른 키의 중복 수령은 거절됐다. 재시작 전 수령하지 않은 골드 우편도 70골드로 지급됐고 원장의 합은 0이었다. 별도 실제 HTTP 경합에서 같은 우편에 서로 다른 키 두 개를 동시에 제출한 결과는 `COMMITTED` 하나와 `CONFLICT` 하나였다. 일반 로그인에서 PostgreSQL 세대 부여, 우편 목록 UI, 캐릭터 프로필과 FastArray의 단일 온라인 권위는 구현이 남았다. [로컬 실행기](../../../Infra/scripts/test-local-native-backend.ps1), [Unreal 서비스 포트](../../../Source/Project_J/Backend/Project_JNakamaServicePort.cpp), [Nakama v3.25.0 HTTP 처리](https://raw.githubusercontent.com/heroiclabs/nakama/v3.25.0/server/api_rpc.go)
- **다른 채널 복귀.** 출발 채널이 비가용 상태면 같은 존에서 사용 가능한 다른 채널을 고른다. 던전이 원래 앵커와 목적 채널을 티켓에 서명하고 수신 서버가 실제 맵·서버 포트·자기 채널과 캐릭터 소유권을 확인한다. 만료 전에는 같은 티켓을 재사용한다. 루프백에서 출발 프로세스를 정상 종료한 후, 원래 예약을 갖고 있지 않은 채널 2에 실제 입장해 원래 위치 복귀를 확인했다. 동일 서버 인스턴스에서는 nonce를 한 번 소비하며, 서버 재시작을 넘어서는 티켓 소비 기록과 채널 heartbeat의 다중 호스트 배포는 후속 경계다. 다른 채널 복귀 증거 (로컬 `Saved/Validation/Continuation_20261014/LocalDungeonSibling_20261123/verification.json`)
- **실제 MainWorld 비행.** 오프스크린 PIE에서 기존 탈것 인스턴스에만 비행을 허용했다. 27초 동안 시작점에서 약 430m 이동했고, 104개 표본에서 비행 상태를 유지했으며 최고 표본 속도는 18.05m/s였다. ## 온라인 로그인·가방과 채널의 PostgreSQL 권위

- **로그인.** `pj_accounts.external_sub`에 `nakama:<사용자 UUID>`가 연결된 계정은 Nakama 사용자 세션으로 자기 캐릭터의 일회용 로그인 티켓을 발급받는다. `ConnectCharacter`는 기존 Nakama 인증에서 받은 토큰과 선택한 캐릭터를 입력으로 받는다. Unreal 서버는 `PostLogin` 이후 플레이어 컨트롤러를 통해 티켓을 받아 현재 채널 세대와 소유권을 확인한다. Nakama 사용자 액세스 토큰은 Unreal 게임 서버로 보내지 않는다. 유효한 세대와 가방 상태를 적용한 뒤 캐릭터를 생성한다. [Nakama 런타임 사용자 컨텍스트](https://heroiclabs.com/docs/nakama/server-framework/introduction/runtime-context/) · [온라인 서버 경계](../../../Source/Project_J/Game/Project_JGameMode.cpp)
- **가방과 우편.** 온라인 캐릭터 가방의 저장은 PostgreSQL이 담당하고 Unreal의 소유자 FastArray는 커밋 결과를 복제한다. 가방의 우편 창에서 받은 아이템은 기존 아이템 ID를 유지한다. 사용·분할·병합·순서 교환에 세션 세대와 영수증을 적용한다. 여러 HTTP 응답의 순서가 바뀌어도 이전 인벤토리 revision으로 덮어쓰지 않는다. 장비·제작 및 기타 온라인 쓰기는 아직 PostgreSQL 커맨드가 연결되지 않았다. [우편 커맨드](../../../Infra/migrations/005_durable_mail_claims.sql) · [가방 커맨드](../../../Infra/migrations/007_online_bag_edits.sql)
- **채널과 복귀.** 지정된 온라인 서버는 실제 경과 시간 기준으로 5초마다 PostgreSQL의 30초 임대를 갱신한다. 새 채널 세대는 이전 세대가 만료된 뒤에 임대를 얻는다. 던전은 복귀 요청 시 같은 구역의 유효한 임대를 읽고 기존 채널 선택 규칙을 적용한다. 목적지 서버에서 서명된 복귀 티켓을 검증한 뒤 로그인 티켓 소비, 캐릭터 세대 증가, 복귀 nonce 저장을 한 트랜잭션으로 처리한다. 실제 Nakama와 PostgreSQL 재시작 후 같은 복귀 nonce로 새 로그인 티켓을 제출해도 거절됐다. [온라인 세션 마이그레이션](../../../Infra/migrations/006_online_world_sessions.sql) · [로컬 실행기](../../../Infra/scripts/test-local-native-backend.ps1)
- **Iris 입장 상한.** 설치형 UE 5.8의 Iris 복제 시스템은 연결 슬롯 128개를 만들며 슬롯 0을 예약한다. 로컬 부하에서 그 한도를 넘을 때 서버가 종료되는 것을 확인했다. 프로젝트 IP NetDriver가 현재 복제 시스템의 상한에서 새로운 소켓을 무시하고, 온라인 채널이 같은 최대 인원으로 등록되게 했다. 한 호스트에서 200개 접속을 시험할 때는 엔진의 기존 Generic 복제 모드를 명시적으로 사용한다. 기본 프로젝트 복제는 Iris를 유지한다. [입장 한도 코드](../../../Source/Project_J/Network/Project_JIpNetDriver.cpp), [로컬 전투 실행기](../../../Scripts/Validation/Run-LoopbackCohort.ps1)
- **실제 클라이언트 저장 회귀.** 로컬 Nakama 사용자 토큰으로 일반 입장한 Unreal 클라이언트가 HUD 우편함에서 지급을 수령했다. 소유 클라이언트가 아이템 ID와 수량 3을 받았고 가방 분할 후 2+1 스택을 관측했다. 총수량과 원본 스택의 PostgreSQL 소유권을 함께 확인했다. [로컬 실행기](../../../Infra/scripts/test-local-native-backend.ps1)
- **200개 실제 연결.** 루프백 Generic 복제 실행에서 Unreal 전용 서버 하나에 독립 게임 연결 200개가 동시에 열렸다. 서버가 클라이언트마다 한 번의 공격을 적용했고, 200건 모두 확인하고 대상 GAS 체력이 0인지 검증했다. 서버와 클라이언트 호스트의 종료 코드는 모두 0이다. 이 결과의 범위는 실제 연결, 소유자 RPC, 서버 피해 적용과 종료다. 200접속 검증 결과 (로컬 `Saved/Validation/Continuation_20261014/LocalBoss200PIETeardown_20261123/verification.json`)

## 신규 테스트 에셋 없이 적용한 온라인 던전·장비·제작

- **온라인 던전.** 월드 포털과 메뉴는 같은 서버 디스패처를 사용한다. 현재 월드의 파티와 세션 세대, 복귀 위치를 기록하고 기존 PostgreSQL 할당 RPC로 예약한다. 목적지 워커의 입장 기록 설치가 확인된 뒤에만 파티에 티켓을 보내며, 접속 목적지에서 서명·캐릭터·워커 세대·활성 예약을 다시 확인한다. 45초 안에 첫 입장이 없는 예약은 풀을 반납한다. 실제 입장이 시작된 워커 세대는 한 던전 실행에 귀속되며, 다시 할당하려면 새 워커 세대가 등록해야 한다. 완료 후 새 워커를 시작하는 책임과 던전 클리어 후크는 호스트·콘텐츠 연결 경계에 있다. [할당 SQL](../../../Infra/migrations/003_dungeon_reservations.sql) · [서버 이동](../../../Source/Project_J/Network/Project_JMMOClientBridgeComponent.cpp)
- **운영 설정.** 두 역할 모두 `OnlineAdvertisedEndpoint`와 세션 저장소를 구성한다. 목적지 워커는 제공하는 정의의 `OnlineDungeonId`와 해당 존의 고유한 `OnlineChannelId`로 등록한다. 참여 게임 서버에 같은 `PROJECT_J_DUNGEON_TICKET_KEY`를 주입한다. 클라이언트는 서명 키를 받지 않는다. 던전 채널은 공개 존 복귀 목록에서 제외한다.
- **장비·제작.** 장착은 가방 아이템 ID를 유지하며 장착 슬롯과 가방 버전을 한 트랜잭션에서 바꾼다. 제작대는 기존 재료·출력 계산을 사용한다. PostgreSQL은 세션과 가방 버전을 비교하고, 즉시 제작의 소비·지급과 시간제 제작의 재료 보관·완료·취소를 같은 저장 경로에서 확정한다. 시간제 제작은 저장된 결과 조건으로 완료하며, 취소 시 원래 재료 ID를 되돌린다. 퀘스트 제작 목표 진척과 기존 UI 에셋 표현은 별도 검증 범위다. [장비·제작 마이그레이션](../../../Infra/migrations/008_online_equipment_and_crafting.sql) · [기존 제작 계산](../../../Source/Project_J/Crafting/Project_JCraftingPlan.cpp)
- **검증.** 실제 Unreal 전용 서버 두 개와 클라이언트 한 개에서 출발, 목적지 입장, 원래 위치로 복귀가 완료됐고 세 프로세스 모두 종료 코드 0이었다. PostgreSQL의 캐릭터 세대는 세 차례 증가했고 예약은 완료로 기록됐다. 실제 Nakama·PostgreSQL에서도 장착·해제, 중복 장착 요청, 시간제 제작의 재료 격리와 취소 후 같은 아이템 ID 반환을 검증했다. SQL 회귀는 만료 예약 재사용, 다른 파티원의 오래된 세션 거절, 즉시·시간제 제작과 재시작 복구를 포함한다. 최종 Editor 증분 빌드, 8모듈 검사, 기존 Standalone 제작 회귀가 통과했다. 최종 빌드 (로컬 `Saved/Logs/ProjectJOnlineDungeonCraftCloseout-EditorBuild-20261123-165642.log`) · [로컬 통합 시험 실행기](../../../Infra/scripts/test-local-native-backend.ps1) · 기존 제작 회귀 (로컬 `Saved/Validation/Continuation_20261014/OnlineCraftingStandaloneRegression_20261123/index.json`)

## 채널별 운영 정원과 로컬 제작 보스 기준선

전용 서버 인스턴스별로 기존 Game 설정에 `OnlineChannelId`와 `MaxTrustedSessions`를 지정한다. 로컬 배포 예시는 채널 3에 설정 정원 200을 요청한다.

```powershell
-ini:Game:[/Script/Project_J.Project_JGameMode]:OnlineChannelId=3
-ini:Game:[/Script/Project_J.Project_JGameMode]:MaxTrustedSessions=200
```

시작 시 설정값을 `UProject_JIpNetDriver`가 보고한 입장 가능 수로 제한한다. 같은 유효 정원을 UE `GameSession`, 신뢰 세션 승인, 비동기 로그인·던전 티켓 대기 상한 및 PostgreSQL 채널 공지에서 사용한다. 기존 채널 임대와 목적지 서버의 합류 검증을 재사용한다. 같은 채널에 활성 플레이어가 있는 동안 정원을 다시 작성하는 동작은 제공하지 않는다. 이 설정은 채널별 운영 정원이며 `Run-LoopbackCohort`의 로컬 최대 200과 독립적이다. [GameMode 설정](../../../Source/Project_J/Game/Project_JGameMode.h) · [승인과 채널 공지](../../../Source/Project_J/Game/Project_JGameMode.cpp) · [로컬 두 채널 검증](../../../Infra/scripts/test-local-native-backend.ps1)

현재 설치형 UE 5.8에서 Iris 연결 저장소는 비공개 `FReplicationConnections` 기본 128슬롯으로 초기화된다. ID 0을 예약해 기존 Project J 드라이버가 읽는 유효 한도는 127이다. 공개 시스템 생성 매개변수에는 연결 수를 설정하는 항목이 없다. 해당 버전의 프로젝트 설정과 공식 API에서 확인된 범위에서는 설정값만으로 확장할 수 없으며, 연결 한도를 지원하는 엔진 버전 또는 소스 엔진 변경이 필요하다. 소스 엔진 경로에서는 연결 ID 배정·회수와 연결별 필터·우선순위·쓰기 상태의 할당을 같은 한도에 맞춰 검증해야 한다. [Epic UE 5.8 Iris 시스템 생성 매개변수](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/IrisCore/UReplicationSystem/FReplicationSystemParams) · [현재 입장 가드](../../../Source/Project_J/Network/Project_JIpNetDriver.cpp)

로컬 PostgreSQL과 Nakama에 연결한 두 Unreal 전용 서버에서 채널 1은 요청 48·유효 48, 채널 3은 요청 256·유효 127을 기록했다. PostgreSQL 채널 임대에 같은 값이 저장됐고, 실제 클라이언트의 일반 로그인과 던전 입장·복귀가 같은 실행에서 통과했다.

`Run-LoopbackCohort.ps1 -BossCombat -MeasureCombat -LegacyReplication`은 기존 Canonical Network 테스트 맵에 `BP_FieldBoss_Test` 한 체와 클라이언트가 소유한 `BP_Spellblade`를 배치한다. 모두 같은 파티로 두고, 같은 서버 틱에 각 클라이언트에 한 번의 근접 공격 입력을 요청한다. 서버에서 연결별 공격자·ASC·대상과 GAS 체력 손실을 대조하고, 각 클라이언트가 최종 체력을 복제받고 종료할 때까지 확인한다. 이전 반복 공격 예비 실행에서 첫 두 공격은 모두 성공했으나 후속 공격에서 서버 궤적 부재와 공격 각도 이탈이 기록됐다. 단발 기준선은 같은 시작 배치의 한 차례 공격을 다룬다. 예비 판정 로그 (로컬 `Saved/Validation/Continuation_20261014/AuthoredBossPilot4Trace_20261123/Server.log`) · [검증 실행기](../../../Scripts/Validation/Run-LoopbackCohort.ps1)

### 배포 환경 분리와 대규모 전투 사례

1. 현재 `-server` 실행 파일과 동일한 시험을 24인 및 32인에서 비교하고, 가능하면 부하 생성기만 별도 PC로 분리한다. 이어 소스 엔진의 Development Server 타깃으로 같은 시나리오를 측정해 서버 빌드 차이를 확인한다. `Project_JServer.Target.cs`는 저장소에 있고 현재 설치 환경에는 독립 서버 실행 파일이 없다. 관측 지표는 틱 시작 간격 p50/p95/p99, 월드 처리 시간, 서버·생성기 CPU 및 메모리, 첫 타격 수신부터 확정 피해까지의 단계별 지연이다. [Epic 전용 서버 설정](https://dev.epicgames.com/documentation/en-us/unreal-engine/setting-up-dedicated-servers-in-unreal-engine)
2. 안정화 구간과 공격 창을 나눠 Unreal Insights의 CPU·네트워크 트레이스를 비교한다. 전체 연결마다 반복되는 후보 수집이 크면 Generic Replication Graph의 공간 및 빈도 노드를 검토한다. 근접 참가자 다수가 모두 관심 범위에 들어오는 구간에는 보스 체력·경고·공격 결과를 우선하고, 원거리 이동과 장식 이벤트의 갱신 비용을 분리한다. 스킬 수신, Mover, 공격 포즈나 타격 판정 시간이 크면 그 경로를 먼저 줄인다. 보스 한 개의 스킬이 여러 참가자를 동시에 타격하는 경우도 별도 측정한다. [Epic Networking Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-insights-in-unreal-engine) · [Epic Replication Graph](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine)
3. 대규모 필드 보스는 한 서버 권위 아래 같은 보스를 공유하는 조건으로 검증한다. 길드워 2는 대형 공개 보스 Tequatl을 운영하고, WvW에서는 네트워크 캐릭터 누락과 렌더링 수준을 구분해 고해상도·저해상도·이름표 표현을 제공했다. Albion 개발팀은 대형 전투 로그로 시나리오를 재현해 스킬 처리 병목을 찾고 지역 혼잡에는 입장 대기열을 둔다. EVE의 B-R5RB는 한 성계에서 최대 2,670명을 기록했고 과부하 시 해당 성계의 시뮬레이션 시간을 늦췄다. 프로젝트의 실시간 근접 전투 목표에는 먼저 원격 표현과 복제 비용을 줄이는 접근을 적용한다. - **전투 권위와 병렬 작업.** `AProject_JWorldEncounter`와 `UProject_JWorldEventRegistry`가 이벤트의 수명과 시작을 관리하고 보스의 전투 상태는 NPC에 둔다. 입력, 충돌 확인, 체력, 처치 및 보상은 기존 서버 권위 경로에 모은다. 거리·후보 점수·경로 계산처럼 읽기 전용 스냅샷으로 계산할 수 있는 작업은 기존 비동기 서브시스템을 사용한다. 공격/이동 세대가 다른 결과는 폐기하고, 게임 스레드에서 제한된 양만 소비한다. 물리 이동, 공격 창, 명중 판정이 공유하는 순서와 시간 기준은 성능 단계에서도 동일하게 검증한다.
- **관심 범위와 복제.** 보스 체력, 위험 경고와 내 공격 결과를 높은 우선순위로 보내고, 원거리 참가자의 장식 상태는 거리와 전투 참여도에 따라 낮은 빈도로 보낸다. 정적인 상태는 변화 시 깨우는 방식으로 휴면을 적용할 수 있다. 근거리 군중의 후보 수집과 채널 생성 비용이 트레이스에서 확인되면 Generic의 공간별 Replication Graph를 비교한다. Iris 경로는 기존 필터와 우선순위 정책을 기준으로 측정한다. 접속 한도와 한 장소에서 모든 캐릭터의 갱신이 필요한 비용은 별도로 기록한다. [Epic 복제 비용과 대역폭](https://dev.epicgames.com/documentation/unreal-engine/performance-and-bandwidth-tips-for-unreal-engine)
- **클라이언트 시각화.** 기존 `UProject_JPresentationBudgetSubsystem`과 애니메이션 예산을 사용한다. 근거리 전투 동작과 보스 예고를 먼저 보존하고, 원거리 캐릭터의 의상·IK·포즈 갱신과 장식 이펙트부터 줄인다. 누락되면 공격을 구분할 수 없는 경고는 현재 복구 가능한 복제 상태를 유지한다. Niagara나 메시 단위의 품질 선택은 클라이언트가 맡고, 서버 공격 판정에 필요한 포즈는 별도 계약으로 보호한다. [Epic Animation Budget Allocator](https://dev.epicgames.com/documentation/unreal-engine/animation-budget-allocator-in-unreal-engine)
