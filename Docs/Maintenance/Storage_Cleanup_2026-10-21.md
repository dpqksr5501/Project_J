## 정리한 범위

플레이어 로코모션 전환 후 저장 공간을 점검했다. 작업 전 논리 집계는 `Saved` 약 42.687GiB, 현재 `Content` 약 61.035GiB, `Intermediate` 약 11.108GiB였다. Git/LFS 이력과 월드 제작 자료도 크지만, 이름·나이·크기만으로 불필요하다고 판정하지 않았다.

두 임시 실험 프로젝트의 `Content`에서 현재 프로젝트 또는 별도 기준 샘플의 같은 상대 경로·크기·SHA-256과 일치하는 사본만 제거했다. 실험 프로젝트는 `Saved/GASP58Migration_20261019/Experiments` 아래의 격리 자료이며 현재 프로젝트의 실행·제작 진입점이 아니다. 각 제거 경로의 절대 위치가 이 두 실험 Content 루트 안인지 검증하고, 제거 직전에 사본과 보존 원본을 모두 다시 해시 비교했다. 재귀 폴더 삭제를 사용하지 않았다.

위 용량은 삭제 파일의 논리 합계다. 삭제 전 드라이브 여유 공간을 같은 조건으로 측정하지 않았으므로 실제 디스크 회수량과 동일한 관측값이라고 주장하지 않는다. 과거 정리에서 확보한 공간을 이번 합계에 더하지 않았다.

제거 후 보존 원본 7,162개를 다시 SHA-256으로 읽어 명세와 일치함을 확인했고, 현재 Content 파일 수도 전후 15,886개로 같았다. 논리 합계·보존 범위·로컬 명세의 지문은 [정리 요약 JSON](Storage_Cleanup_2026-10-21.json)에 남겼다.

실험 사본은 이제 완전한 독립 프로젝트 백업이 아니다. 다시 구성하려면 로컬 명세의 counterpart/해시를 기준으로 보존 원본에서 누락 파일을 복사해야 한다. 고유 에셋과 Source/Config·실험 메타데이터는 유지한다. 로컬 상세 명세·제거 journal·검증은 `Saved/StorageCleanup_20261021`에 있으며, Git으로 옮기지 않는 외부 기준 샘플의 현재 위치도 그 명세에만 기록한다.

## 문서의 현재 기준

포트폴리오와 제작 진입점은 [플레이어 로코모션 아키텍처](../Animation/Architecture/Player_Locomotion_Architecture.md)로 정리했다. Mover·C++ 상태/핀 계산·ABP 평가 시점·공용 모션·몸체별 보정의 실제 책임을 설명한다. 외부 샘플/모션/엔진 노드의 출처와 프로젝트에서 통합한 범위를 별도 절에 명시했다. 샘플을 자체 제작한 것처럼 바꾸지 않았다.

기존 이관 문서는 [플레이어 로코모션 전환·검증 기록](../Animation/Architecture/Player_Locomotion_Migration_2026-10-19.md)으로 이동하고 옛 경로는 안내로 남겼다. 실제 runtime 에셋·코드·Saved 경로의 이름은 문서 표현 정리와 함께 변경하지 않았다. README·프로젝트 개요/맥락·애니메이션/제작/이동 목차·확장·골격/IK·전투·원격 이벤트의 현재 설명을 갱신했다. R19/R20·CMC/MM·과거 성능과 현재 구조를 구분한다.

전체 문서의 로컬 링크와 현재/과거 진입점을 검사했다. 작업 전 74개 오류 중 5개는 검사기가 URL 인코딩된 한글·공백 경로를 해석하지 못한 경우였고, 1개는 루트 README의 퇴역한 궤적 소스 링크였다. 나머지 68개는 당시 Source/Scripts 경로를 텍스트로 보존하고 현재 안내를 연결했다. 과거 기록의 실패·측정값·원본 비교는 삭제하거나 새 구조의 통과 결과로 바꾸지 않았다. 전체 문서의 모든 API·설계·수치를 새 runtime에서 재검증한 것으로 확대하지 않는다.

현재 정의와 대조하다 발견한 소모품 제작 설명도 실제 `UProject_JConsumableDefinition`과 사용 요청/소유자 재검증 경로로 수정했다. UI의 이전 CMC SavedMove 수정은 현재 Mover 입력 승인과 구분했다. 단순 이름 검색만으로 제안·제거 이력을 현행 API 오류로 처리하지 않았다.

큰 안내/제작 본문을 갱신하기 전 작업 사본 10개는 [원문 ZIP](../Archive/Navigation/2026-10-21/Before_Current_Documentation.zip)과 [SHA-256 명세](../Archive/Navigation/2026-10-21/Preservation.json)로 보존했다. 전체 목록은 기존 생성기로 재생성하며, 링크 검사와 `git diff --check`를 수행한다. 저장소 밖의 선택적 Worktrees 증거 12개는 현재 없는 로컬 자료로 구분하며 가짜 파일이나 근거를 만들지 않는다.

카탈로그 생성기가 기존 World/WorldGen 및 새 주제의 문서를 목록에서 누락할 수 있던 부분도 수정했다. 문서 시작점·월드 주제를 포함하고, 새 주제도 기본 항목으로 표시한다. 바뀐 현재 가이드로 향하는 절 앵커와 보존 ZIP의 해시도 별도로 확인한다.

이번 변경은 문서·문서 검사기·동일 임시 사본 정리다. runtime 코드/에셋 변경이 없어 Unreal 빌드·PIE를 다시 실행하지 않았다. 이전 IK 작업의 61개 native/실제 플레이 결과를 새 실행으로 보고하지 않는다. 정리 시작 시 관련 editor/build/game 프로세스가 없었고, 이번 작업에서 에디터를 열지 않았다.

## LFS 임시 사본 급증과 재발 방지

이후 별도 조사에서 `.git/lfs/tmp`의 601개 파일이 논리 합계 128,897,889,280 bytes인 것을 확인했다. 비어 있지 않은 589개 전부의 앞·뒤 표본이 보관 ZIP과 일치했고, 같은 시간 Codex 앱 로그에는 이 미추적 ZIP을 포함한 `git diff --no-index`의 반복 중단과 디스크 부족(`ENOSPC`)이 남았다. 애니메이션 원본이나 Codex 오류 로그 자체의 증가와 구분한다.

사용자의 명시적 정리 요청에 따라 보관 ZIP의 SHA-256을 명세와 확인한 뒤, ZIP 하나만 정상 LFS 포인터로 스테이징했다. `.gitattributes`의 해당 보관 ZIP 규칙은 `filter=lfs -diff merge=lfs -text`로 바꿨다. 인덱스의 포인터는 134 bytes이며 원래 ZIP은 393,590,513 bytes 그대로다. 이 작업은 커밋·push가 아니다. `-diff`만으로 clean filter 실행을 막는다고 보지 않고, ZIP을 미추적 파일 자동 비교에서 제외하는 인덱스 등록과 함께 적용했다. [새 보관 ZIP 처리 기준](../../Archives/AnimationSources/README.md#보관-zip의-git-비교와-임시-파일)을 따른다.

정리 직전 기록은 임시 파일 557개 / 120,332,223,488 bytes다. 조사 시점과 이 값의 차이를 이번 삭제량에 합산하지 않는다. 각 후보의 절대 경로·재분석 지점 여부·크기·수정 시각과 안정 시간을 확인하고, Git/LFS 실행이 없는 구간에 배타적 파일 핸들로 열었다. 보관 ZIP의 해당 접두 구간과 **파일 전체 바이트**를 비교한 경우에만 같은 핸들로 제거했다. 안정된 빈 파일도 같은 경로/핸들 검사를 적용했다. 진행 중 다른 Git 조회가 감지돼 중단한 뒤 기존 journal과 보존 기준을 확인하고 재개했다. 프로세스 강제 종료·재귀 삭제·LFS prune은 수행하지 않았다.

이번 상세 후보·파일별 SHA-256/삭제 journal·보존 전후 fingerprint·diff 확인·잠금 소유자·여유 공간 기록은 로컬 `Saved/Maintenance/LfsTemporaryCleanup_20261021`에 둔다. 삭제한 부분 사본은 완전한 원본이 아니며 보존 ZIP에서 같은 접두 바이트를 재구성할 수 있다. 런타임 코드·애니메이션·보관 원본을 변경하지 않았으므로 Unreal 빌드·PIE는 수행하지 않는다. 공유 가능한 재발 방지 설정과 절차만 저장소 파일로 유지하며 Codex 앱 바이너리나 개인 전역 설정은 수정하지 않는다.

### Google Drive 업로드 사본과 최종 회수

사용자가 기존 여유 공간이 Windows 표시 약 150–160GiB였다고 알려 추가 확인했다. 같은 날 12:19의 이전 정리 기록에는 실제 여유 공간 172,833,906,688 bytes(약 161GiB)가 있어, 첫 LFS 정리만으로 회수가 완료됐다고 볼 수 없었다. 휴지통·Google Drive 앱 캐시·프로젝트 증가분을 먼저 확인한 뒤 사용자 폴더의 최근 생성 파일 메타데이터로 범위를 넓혔다.

`Documents/.tmp.driveupload`에서 730개 / 106,181,346,695 bytes를 발견했다. 그중 473개 / 105,686,885,376 bytes는 보관 ZIP 접두 구간의 앞·뒤 표본과 일치했다. LFS 임시 파일의 부분 사본이 Google Drive의 문서 동기화 과정에서 별도 업로드 사본으로 남은 것이었다. 이 업로드 폴더에는 다른 파일도 섞여 있어 직접 삭제하지 않았다. Google Drive 프로세스의 삭제 대기 파일 핸들 조회에서는 큰 보존 파일이 확인되지 않았으며, 업로드 폴더 자체의 실제 사본으로 원인을 좁혔다.

사용자가 트레이에서 Google Drive를 정상 종료한 뒤 업로드 폴더가 0개 / 0 bytes로 비워지고 여유 공간이 약 203.6GB로 돌아온 것을 확인했다. 이는 Google Drive 종료에 따른 자체 처리이며 이 작업이 업로드 큐를 강제로 지운 결과가 아니다. 종료가 완료돼 마지막 LFS 임시 파일 3개의 잠금도 풀린 뒤 원래 ZIP과 전체 바이트 비교·배타적 핸들 검사를 재적용해 제거했다.

- 최종 LFS 임시 파일 삭제는 누적 **557개 / 120,332,223,488 bytes**이며 `.git/lfs/tmp`는 0개다.
- 최종 C: 여유 공간은 **204,344,762,368 bytes**, 약 **204.3GB / 190.3GiB**다. 첫 정리 시작의 78,161,522,688 bytes보다 관측상 126,183,239,680 bytes 증가했다. 서로 중복되는 LFS/업로드 사본의 논리 합계를 실제 회수량에 더하지 않는다.
- Content와 정상 LFS 객체의 전체 경로·크기·수정 시각 fingerprint, 보관 ZIP과 해당 정상 LFS 객체의 전체 SHA-256은 최초 보호 기준과 다시 일치했다. 정상 LFS 객체나 애니메이션을 추가 삭제하지 않았다.
- Google Drive가 종료된 상태와 임시 폴더 0개를 확인했다. 앱을 자동 재시작하거나 개인 동기화 설정·백업 범위를 변경하지 않았다. 기존 ZIP의 인덱스 등록과 바이너리 diff 규칙으로 원래의 반복 diff 입력을 제거한다.

업로드 사본의 표본 비교는 용량 원인 조사 증거이며 파일별 완전 무결성 검증으로 확대하지 않는다. 직접 삭제한 LFS 파일에는 표본 비교보다 강한 전체 바이트 검증을 적용했다. 로컬 `DriveUploadAudit.json`과 최종 `Result.json`이 이 단계의 근거다.
