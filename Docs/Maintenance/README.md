# 문서 관리와 보존 규칙

## 분류 기준

먼저 주제를 고르고, 그 주제 안에서 문서 종류를 고른다. 애니메이션·전투·게임플레이·네트워크·성능은 각각 한 진입점을 사용한다. Architecture에는 여러 주제의 공통 런타임·확장·전체 계획을 둔다.

| 폴더 종류 | 작성할 내용 |
| --- | --- |
| Architecture | 책임·소유권·데이터 흐름·계약·구현과 보류 범위 |
| Authoring | 에디터·DA·ABP·소켓·콘텐츠 제작 순서 |
| Diagnostics | 증상·재현·로그·원인·수정·측정 한계 |
| CaptureGuides | 실제 측정·로그를 수집하는 절차 |
| Planning | 제안·조건·우선순위·도입 게이트 |
| Reports / Baselines / Validation | 시점별 변경·검증과 대응 원본 |
| Review | 감사·검토·작업 요청과 후속 결과의 흐름 |
| Handoffs | 당시 브랜치·진행 상태·이어갈 작업 |
| Archive | 대체된 안내·중복 자료의 원문 보관 |

빈 종류 폴더는 미리 만들지 않는다. 종류가 섞인 기존 문서는 본문을 유지하고 목차에서 범위를 설명한다. 예를 들어 MotionMatchingNextSteps는 현재 계약과 후속 계획을 모두 포함한다.

## 기준 내용과 중복 관리

1. 주제 README는 작업별 읽는 순서와 문서 링크를 제공한다. 상세 설정·운영 지침은 담당 문서에 둔다.
2. 소유권·계약은 구조 문서, 에디터 단계는 제작 문서, 당시 수치는 검증·진단 기록을 기준으로 삼는다.
3. 다른 문서의 설명을 복제하기보다 해당 기준 위치로 연결한다. 기존 고유 내용·원인·시도·수치·출처를 보존한다.
4. 중복 본문을 통합할 때에는 원문을 Archive 또는 해당 날짜의 보고서에 먼저 보존하고, 기준 문서에 원문·후속 결과 링크를 남긴다.
5. 날짜만으로 최신 기준을 선정하지 않는다. 변경된 역할은 최신 코드·Config와 결과에 근거해 표시하고 과거 판단은 당시 기록으로 남긴다.

## 검증과 증거

- 빌드·자동화·에디터 컴파일·사용자 플레이·네트워크 실측·성능 실측의 증거를 구분한다.
- 검증에는 날짜·커밋 또는 작업 상태·명령·조건·결과·한계를 기록한다. 서로 다른 실행의 통과 수나 개선율을 합산하지 않는다.
- CSV·JSON·스크립트·체크섬·보고서의 관계를 유지한다. generated 카탈로그의 원본 JSON과 생성 경로는 임의로 변경하지 않는다.
- 저장소 밖 Saved/Worktrees 증거는 로컬 기록으로 구분한다. 파일이 없다는 이유로 과거 수치나 링크를 삭제하지 않는다.

## 이동·새 문서 작성 절차

1. 새 문서는 적절한 주제·종류에 하나의 기준 위치로 작성하고 그 주제 README에 연결한다.
2. 이동할 때 상대 링크, 루트 README, 본문의 저장소 경로, Source·Config·스크립트 참조와 생성기를 확인한다.
3. 의미 있는 제목·역할·근거를 유지한다. 이름을 바꿀 경우 이전 경로와 새 경로를 변경표에 기록한다.
4. 전체 목록은 `node Scripts/Documentation/Update-DocumentCatalog.mjs`로 갱신한다.
5. `node Scripts/Validation/Validate-DocLinks.mjs`와 `git diff --check`로 확인한다.
