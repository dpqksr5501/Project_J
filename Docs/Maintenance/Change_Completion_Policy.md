# 변경 마감·중복과 레거시 관리

## 목적과 적용 범위

버그 수정·기능 추가·리팩터링 이후에 교체한 코드, 중복 실행 경로, 이중 상태와 임시 예외가 남는 것을 줄인다. 이름이나 파일 수가 아니라 **실제 호출·데이터 소비·상태 소유권·수명**으로 판단한다. 적용 대상은 프로젝트가 소유하거나 참조하는 **모든 소스·설정·에셋과 제작/로드/배포 연결**이다. 본문에 열거한 타입은 예시이며 대상의 한정 목록이 아니다. 새 에셋 종류에도 같은 원칙을 적용한다.

예를 들어 BP/ABP·DA/DT·Chooser·입력·노티파이뿐 아니라 애니메이션/몽타주/커브·스켈레톤/리타깃/리그/물리, 메시/머티리얼/텍스처·Niagara·오디오/MetaSound·UI/폰트, 레벨/월드 구성·배치 Actor·플러그인 콘텐츠·임포트/생성 자원도 포함한다. 타입별로 어떤 참조·상속·override·생성·등록 경로를 쓰는지 확인한다. 엔진/외부 플러그인 원본은 사용 계약을 확인하되 임의로 수정·정리하지 않는다.

[AGENTS.md](../../AGENTS.md)는 자동 작업자의 짧은 진입점이고 이 문서가 상세 판단 기준이다. 현재 시스템 책임은 [프로젝트 맥락](../Overview/ProjectContext.md), 구체적인 계약·제작 절차는 각 주제의 기준 문서를 따른다. 최신 사용자 요청과 보존 조건을 우선한다.

MCP·컴퓨터 사용은 현재 요청 수행에 필요하면 별도 도구 사용 허락 없이 활용한다. 같은 요청의 구현·검증에 필요한 관련 변경·저장도 도구를 쓴다는 이유로 반복 승인받지 않는다. 작업 범위 밖 기능 구현·에셋 삭제·전체 감사·커밋/push를 자동으로 추가하는 권한은 아니며, 사용자 변경 보존·접근 제한·도구 자체 승인 정책과 빌드 안전 규칙은 유지한다. 상세 도구 선택·조회 범위 기준은 AGENTS.md를 따른다.

검토는 **변경한 기능과 직접 연결된 흐름**부터 한다. 공통 결함이 확인되면 같은 계약의 호출 전체로 넓힌다. 작은 수정마다 전 시스템을 재감사하거나 기존 구현을 다시 만드는 규칙이 아니다.

## 작업 흐름

1. 현재 Git 상태·사용자 변경·실행 프로세스를 확인하고 관련 구조/제작 문서와 기존 검증을 필요한 만큼 재사용한다. 다른 채팅의 현재 변경도 보존한다.
2. 증상/요구 → 호출자와 데이터 입력 → 권위 있는 상태 → 실제 소비 → 완료/취소/실패/종료를 연결한다. 헤더·inline·override·BP 호출도 영향에 따라 포함한다.
3. 기존 구현·공통 계약으로 해결할 수 있는지 확인하고, 추가할 상태/분기/에셋의 책임을 설명한다. 원인과 관계없는 새 추상화·범용 프레임워크를 만들지 않는다.
4. 최소한의 호환 변경을 구현하면서 교체된 옛 경로의 잔여 호출·writer·구독·등록/해제·fallback을 함께 확인한다. 실제 삭제·통합은 아래 근거와 허용 범위를 충족할 때만 한다.
5. 영향받는 기능을 검증하고 기준 문서에 달라진 계약을 반영한다. 결과는 기존 보고나 변경 설명에 짧게 남긴다. 별도 전수 목록·새 JSON 장부는 범위가 실제로 필요할 때만 만든다.

## 무엇을 중복으로 판단하는가

| 대상 | 확인할 근거 | 유지할 수 있는 이유 |
| --- | --- | --- |
| 함수·분기·fallback | 실제 caller/override, 같은 입력·조건·부작용, 성공/실패 출력과 최종 소비 | 경계 검증, 서로 다른 오류 복구, 호환 버전, 다른 권위에서 필요한 재검증 |
| 상태·캐시 | 누가 언제 쓰고 읽는지, 원천에서 계산 가능한지, 갱신/무효화 시점 | GT→worker snapshot, 서버/예측 상태, 표현 지연, 재진입 방지, 실제 비용을 줄이는 캐시 |
| 에셋·구성 데이터·데이터 행 | 실제 소비자·참조·상속/override·적용 순서·기본값·소유자, soft/dynamic 로드와 등록 | 직업/무기별 독립 튜닝, 제작 variant, fallback, 조건이 다른 필수 선택 행, 테스트 fixture |
| 리소스·그래프·월드 구성 | 공유 원본과 instance의 역할, 그래프 연결·파라미터·의존 자원, 배치/로드·생성 경로와 출력 | 같은 외형이라도 다른 재질·물리·음원/표면·플랫폼 설정, 월드/제작 맥락, 재임포트 원본·의도된 생성 결과 |
| 노티파이·NotifyState | 실행 클래스, payload/override, 시간/구간, trigger weight, LOD/filter, 취소/End 부작용, 클라이언트/서버 역할 | 다른 발/소켓/이벤트, 별도 구간, legacy payload 변환, 편집 미리보기와 runtime의 차이 |
| BP와 native의 유사 구현 | 실제 활성 graph/핀·상속 override와 native 호출, 동일 이벤트의 이중 실행 | 에디터 전용 표시, 선택적 확장 hook, 서로 다른 pawn/실행 모드 |

같은 클래스의 DA 두 개나 같은 clip을 출력하는 Chooser 행은 그 사실만으로 중복이 아니다. 같은 메시·텍스처·사운드나 유사한 그래프를 쓰는 에셋도 override·제작·로드 역할이 다르면 별도로 유지할 수 있다. 반대로 다른 이름이어도 동일 owner에게 같은 능력을 두 번 부여하거나 같은 이벤트에서 같은 상태를 두 번 쓰면 결함일 수 있다. 값/외형이 같다는 것과 책임이 같다는 것을 구분한다.

서버 검증과 클라이언트 예측, 원천 상태와 immutable snapshot을 단순히 하나로 합치지 않는다. 유지할 역할이 확인되면 그 이유를 기준 문서나 해당 변경 설명에 남긴다.

## 미사용 확인과 안전한 퇴역

- C++ 텍스트 검색 외에 UFUNCTION/UPROPERTY·delegate·인터페이스·상속 override·console/automation 진입점과 BP/ABP의 실제 연결을 필요에 따라 확인한다. 주석·선언·파일 목록만으로 실행 사용을 입증하지 않는다.
- 에셋은 hard/soft reference, 문자열 경로·Config·AssetManager/PrimaryAsset 규칙, DT/Chooser의 결과/fallback, 클래스 기본값·부모 BP·몽타주/시퀀스 노티파이, Cook·제작 도구·테스트의 연결을 영향 범위에서 확인한다. 검색 결과 0은 삭제 근거의 일부일 뿐이다.
- 위 참조 예시에 해당하지 않는 에셋도 사용처 확인을 생략하지 않는다. 해당 타입의 그래프/리소스 의존성, instance override, 월드·외부 Actor 연결, 플러그인 등록, 임포트·생성 과정 등 실제 소비 경로를 확인한다. 특정 목록에 없다는 이유로 미사용 처리하거나 작업마다 무관한 모든 에셋을 전수 조회하지 않는다.
- 테스트·샘플·prototype·의도적으로 비활성화한 제작 자산은 미참조만으로 삭제하지 않는다. 삭제가 요청되지 않았다면 역할과 위치를 기록하고 보존한다. 보존을 위해 무조건 새 runtime 참조나 Cook root에 등록하지도 않는다.
- 대체 경로가 있다면 같은 입력의 결과·부작용·실패/취소/종료를 비교한다. 구독·timer·async callback·입력/능력 grant·lease는 소유자의 해제와 재진입까지 확인한다.
- 반영 클래스·직렬화 필드·DA/노티파이를 교체할 때에는 기존 BP/에셋·저장 데이터와 배포 호환을 고려한다. 필요한 경우 기존 payload 보존, 변환, redirect와 사용처 이주를 검증하고, 새 클래스가 컴파일됐다는 이유만으로 이전 클래스를 삭제하지 않는다.
- 에셋 삭제·이름/경로 이동은 허용 범위 안에서 참조 이주·redirector 처리·필요한 저장/검증까지 묶는다. 접근 제한을 우회하거나 바이너리 내부 문자열을 직접 치환하지 않는다.
- 임시 호환 경로에는 담당 계약·남은 소비자·제거 조건을 남긴다. 근거가 부족하면 `미확정 후보`로 기록하고 사용하지 않는 코드라고 단정하지 않는다. 미래의 막연한 필요만으로 새 추상화를 미리 늘리지 않는다.

## 원인 수정과 구조 보존

증상을 숨기는 강제 reset·timer·특정 키/클립 예외 대신 입력, 권위/소유권, snapshot 게시, 선택·재생, 취소/완료 중 어느 계약이 어긋났는지 먼저 확인한다. 새 예외가 필요하면 기존 공통 계약으로 해결할 수 없는 근거와 적용 경계를 설명한다.

MMORPG의 서버 권위·예측과 클라이언트 표현, Avatar 교체·재접속·월드 종료, GT/worker·GC·늦은 callback의 유효성을 관련 변경에서 확인한다. 사용하지 않는 대규모 서비스나 새 전역 manager를 추가하는 것이 확장성 개선은 아니다. 기존 모듈 의존성과 owner/lease 계약을 재사용한다.

애니메이션 변경은 기존 [애니메이션 기준](../Animation/README.md)을 따른다. 선택 asset의 존재, graph 분기 도달, 실제 pose/화면은 서로 다른 증거다. 입력 의미·발/손 접촉·notify·단발/MM 복귀와 기존 OTM/Strafe·TIP 등 영향을 받는 계약을 보호하고 수치만 통과한 결과를 시각 품질 승인으로 바꾸지 않는다.

## 검증은 변경 위험에 맞춘다

| 변경 | 필요한 검증의 기준 |
| --- | --- |
| 문서·주석만 변경 | 링크·생성 목차·diff 확인. runtime 빌드/전체 회귀는 필요하지 않다. |
| C++ 동작·상태 소유권 변경 | 관련 target 빌드와 재현/집중 회귀. 해제·실패·재진입 등 실제 위험에 맞는 사례를 포함한다. |
| 모든 종류의 에셋·구성·연결 변경 | 해당 타입의 실제 소비/출력과 기존 값·payload·override 보존 확인, 영향 기능 실행. native 빌드 성공만으로 에셋 검증을 대체하지 않는다. |
| 직렬화·로드·Cook root·플랫폼/반영 경계 변경 | 위험에 따라 Game/Cook/패키지 또는 데이터 이주 검증을 추가한다. 에디터 로드만으로 배포 가능을 판정하지 않는다. |
| 공통 실행·복제·예측 계약 변경 | 같은 계약의 호출 전체와 필요한 통합/작은 원격 회귀를 추가한다. 성능/부하는 요청 또는 실제 변경 위험이 있을 때 수행한다. |

호환되는 수정을 묶어 빌드하고 각 변경의 집중 회귀를 연결한다. 전체 회귀·Game/Cook/패키지는 통합 기준점이나 변경 위험상 필요한 경우에 수행한다. 동일 소스·에셋·바이너리와 조건의 유효한 기존 근거는 재사용하고, 새 변경·실패·미해결 우려가 없으면 반복하지 않는다. 실행 대기 중에는 기존 source/asset을 바꾸어 검증 대상과 결과의 대응을 흐리지 않는다.

테스트는 회귀를 막는 실제 계약·경계·부작용을 확인한다. 구현을 그대로 복제한 테스트나 문서 변경만을 위한 native 테스트는 추가하지 않는다. 기존 fixture/공개 API를 우선하고 전용 우회 경로를 만들지 않는다. 기존 테스트 소스와 fixture 데이터는 영구 자산이며 일회성 실행 스크립트·캡처·세션 파일과 구분한다.

Unreal 빌드의 directUBT·정상 종료·프로세스 겹침 금지는 [AGENTS.md](../../AGENTS.md)를 따른다. 최초 오류와 실제 컴파일 작업 수·증분 상태를 먼저 확인하며 빌드가 느리다는 이유로 중단·동시 실행·전체 캐시 삭제를 하지 않는다.

## 결과의 최소 기록

작업 결과에 다음 네 항목을 구분한다. 작은 변경은 커밋/PR 설명이나 기존 결과 문서의 짧은 항목으로 충분하다.

- **실제 변경:** 무엇을 왜 수정·통합·제거했고 어느 경로가 기준이 됐는가.
- **검토 후 유지:** 유사해 보이는 구현/데이터를 유지하는 책임·수명·제작/테스트 이유.
- **검증:** 대상 source/asset 기준, 실행 조건과 결과. 새 실행과 재사용한 기존 근거를 구분한다.
- **남은 경계:** 미검토, 환경/접근 미검증, 미확정 후보, 사용자 보류/제외를 구분한다.

파일 수·검색 성공·자동화 통과를 모든 함수·에셋의 정밀 완료로 해석하지 않는다. 범위에서 제외한 항목은 해결 완료가 아니다. 과거 보고와 실패 근거를 지우지 않고 실제 책임/제작 계약이 달라진 담당 문서만 갱신한다. 문서 배치·보존·카탈로그는 [문서 관리 규칙](README.md)을 따른다.

## Git 공유와 작업환경 변경

- 현재 규칙은 저장소 루트의 AGENTS.md와 이 문서 한 곳에서 관리하고 [문서 시작점](../README.md)에서 연결한다. 사람과 AGENTS.md를 자동 적용하지 않는 도구도 같은 기준을 찾을 수 있게 한다.
- 실행에 필요한 Source·Config·실제 에셋·영구 테스트와 기준 문서는 Git에 포함한다. 엔진 설치 경로·사용자 홈·드라이브·로컬 플러그인을 문서의 필수 전제로 고정하지 않는다. 프로젝트 기준 상대 경로와 실제 환경 확인 방법을 사용한다.
- 새 PC에서는 .uproject·target/configuration·엔진/플러그인 요구와 Git LFS 원본 수신을 확인한다. LFS pointer를 실제 에셋으로 취급하지 않으며, 커밋 시에는 변경 에셋의 원본과 LFS object가 연결되는지 확인한다.
- 임시 실행 파일·로그·MCP 세션·캡처·바이너리·캐시는 기존 ignore 규칙을 따른다. 필요한 재현 조건·요약·원자료 지문만 남기고 token·계정·개인 SaveGame·환경 비밀값을 커밋하지 않는다. 로컬 원자료만으로 새 PC에서 재현할 수 있다고 주장하지 않는다.
- 실행별 격리 디렉터리의 재생성 캐시와 패키지·PDB·전체 trace를 모두 영구 보관하지 않는다. 실행 종료/사용 중 여부를 확인하고 유효 기준점·비교·미해결 분석에 필요한 대표 원자료를 선별한다. 현재 빌드 캐시와 테스트 자산을 일회성 산출물과 구분한다.
- 허용 범위에서 원자료를 퇴역할 때에는 요약·조건·원본 지문·남긴 위치와 재실행/재분석이 불가능해진 범위를 기록한다. 논리 크기 합계를 실제 확보 용량으로 보고하지 말고 하드링크·공유 데이터와 드라이브 여유 공간 전후 값을 구분한다. [정리 사례](Storage_Cleanup_2026-10-16.md)를 참조한다.
- 커밋 전 변경 파일을 명시적으로 검토하고 사용자 변경과 임시 파일을 분리한다. 버전 이력을 지우거나 테스트 자산을 일괄 정리하지 않는다. 커밋·push·병합은 해당 요청의 허용 범위를 따른다.

이 규칙의 효과는 다음 실제 변경에서 확인한다. 반복해서 놓치는 계약이 생기면 해당 기준을 보완하되, 중복 체크리스트·작업별 정책 파일·필수 대규모 검증을 계속 늘리지 않는다.
